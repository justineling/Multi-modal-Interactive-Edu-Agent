为什么服务层不依赖 HTTP

所有业务逻辑在 services/ 里，api/ 只做三件事：解析请求、调用服务、包装响应。 好处是服务层可以被测试直接调用（不需要起 HTTP 服务），也可以被脚本、定时任务、CLI 复用。

240 个测试里有相当一部分是直接调服务层函数的，跑得比 HTTP 测试快一个数量级。

四种核心设计模式

模式一：受控 DSL 驱动渲染（Schema-Driven Strategy）

严禁 LLM 直接输出 HTML / Three.js / Manim 源码。

LLM 只填 JSON，前端按 type 字段策略分发到对应渲染器：

// 前端 ArtifactHost.tsx 的核心逻辑
switch (spec.type) {
  case "ppt":      return <SlideRenderer spec={spec} />;
  case "anim_2d":  return <Anim2DRenderer spec={spec} />;
  case "scene_3d": return <Scene3DRenderer spec={spec} />;
}
对比项让 LLM 写代码受控 DSL（本项目）
成功率十次有八次出问题（镜头穿模、材质丢失、语法崩溃）100%，渲染器是确定性代码
出图速度服务端渲染 30~60 秒前端毫秒级
可交互视频没法交互每个元素都是 React 组件，可点击可 hover
安全性要沙盒执行任意代码只解析 JSON，无代码执行

模式二：双轨知识路由（Corrective RAG + Router）

检索后先做相关性评估，输出三态，决定回答的边界：

状态触发条件回答结构
SYLLABUS_MATCH实词命中率 ≥ 0.45 且分数足够高，或显式章节锚定命中严格课本 + 逐条页码
PARTIAL_OR_BEYOND实词命中率达标但分数不足课本基准 + 深度拓展双层
NO_MATCH实词命中率 < 0.45明确"未覆盖"，citations = []

详细算法见 检索与路由。

模式三：画布增量补丁（Command / JSON-Patch）

产物不是整份重生成，而是接收增量操作指令：

{
  "op": "update_node",
  "node_path": "/slides/2",
  "payload": { "bullets": ["..."], "speaker_notes": "..." }
}

payload 只带被修改的字段，前端做字段级 merge。 后端用 deepcopy + 定点写入，保证其余节点字节级不变。 详细见 增量补丁与 SSE。

模式四：节点锚点双向绑定（Bidirectional Context Binding）

PPT 每页、2D 每个元素、3D 每个部件都有唯一路径（/slides/2、/steps/1/entities/3、/nodes/5）。 点击时前端构造锚点，把路径 + 页码 + 章节号注入输入框上下文。

这个设计把"用户指着某处说话"这个自然行为，翻译成了机器能理解的精确定位。

一次请求的完整协作链

用户在输入框按回车后，按顺序发生这些事：

  1. 前端建立 SSE 连接

    POST /api/chat/stream，body 含 workspace_id、query、mode、anchor。 用 fetch + ReadableStream 读，不是 EventSource（它不支持 POST）。

  2. 后端发 turn_start

    携带 demo_mode、has_anchor、mode。前端建占位消息，开始流式态。

  3. 检索 + 评估

    章节号精确过滤 → BM25 + 向量混合检索 → 实词命中率门槛 → 输出三态之一。发 retrieval 事件。

  4. 形态路由

    根据问句语义判断该出 PPT / 2D / 3D，同时给出人话理由。发 modality_decision 事件。

  5. 生成正文（流式）

    逐 token 发 token 事件。严格模式每句带页码；拓展模式分两层。

  6. 生成 JSON AST

    Pydantic 校验，失败则把错误回灌给模型重试（最多 3 次），全失败降级到 mock。

  7. 落库 + 发 artifact

    写 artifacts + artifact_versions 两张表，发完整 spec（create）或补丁（patch）。

  8. 发 citations 与 turn_end

    引用按书页顺序；turn_end 带真实耗时与版本号。消息落库供刷新恢复。

事件顺序是契约：turn_start → retrieval → modality_decision → token* → artifact? → citations → turn_end。 error 可插入任意位置，但之后仍必须补发 turn_end——否则前端会一直以为还在生成，输入框永远禁用。

并行生成与模型分档（P1-03）

真实模式下整轮曾要 66.3 秒，右侧画布空白近 70 秒。剖析后发现瓶颈非常集中： 83.7%（55.5s）是一次 complete_json，其中 36~54 秒是模型「思考」； 检索 + 路由 + 引用 + 落库合计不到 14 毫秒。

这个数字直接推翻了一个原定方案：v1.0 打算「分批下发，先出前 2 页」，但实测 2 页需 36.5 秒—— 瓶颈是思考时长，不是输出长度，分批根本改不了瓶颈。方案已归档为 P1-03-latency-PRD.v1.0.md。

两个改动

改动做法效果
产物换轻量档 新增 LLM_MODEL_ARTIFACT（默认 deepseek-flash）。 不改 GENERATOR 的默认值——那个变量的语义是「复杂 AST 用大模型」， 改它会让 README / .env.example / 架构文档三处同时变成假话 55.5s → 10.1s
契约通过率不变（11 回合 0 重试）
正文/产物并行 两者互不依赖，用 asyncio.Task 并行。ARTIFACT_FORK_MODE=after_first_token 省 10.8s

fork 点为什么必须在首 token 之后

如果产物分支和正文同时启动，两者会争抢同一个上游连接与事件循环，TTFT 会被产物耗时污染。 after_first_token 保证「首字延迟」与「产物生成」在时序上解耦：用户看到文字时，产物才刚开始跑。

这个不变量有测试锁着（test_artifact_parallel.py）：用 spy 记录产物分支的进入时刻， 断言它晚于首个 token 事件被消费的时刻；另外还有一条反向验证——切到 immediate 模式时断言方向反转， 证明测试有区分力而不是恒绿。

换档暴露的连带问题：页码静默编造

换档后出现了一个更隐蔽的问题：所有 slide 的 source_ref 都写 p.76， 而真实页码可能是 83~91。根因是三件事叠在一起：

  1. _artifact_prompt 从不把页码告诉模型（正文切片里一个页码都没有）
  2. 契约示例里硬编码了 "source_ref":"4.1.1, p.76"，轻量模型原样照抄
  3. facts 与 pages 之间没有对应关系，模型即使想标也标不出

换档前重档模型是「明显缺失」（根本不写页码），换档后变成「看起来对但是假的」——后者危险得多。 修法是 _clamp_spec_pages：落库前把落在检索命中页之外的页码剥掉。

钳制 ≠ 后校验，两者管不同的东西：

  • _drop_invalid_citations 管正文里的 [p.N]——不篡改已流出的正文，只剔除引用
  • _clamp_spec_pages 管产物 AST里的页码——落库前剥离，不触发重试（编造页码重试三次还是编）

两者共用 result.pages 作为「哪页合法」，口径必须一致。patch 路径也要钳制—— update_node 的 payload 可能只带 {"source_ref": "4.3.1, p.76"}， create 钳了 patch 不钳，用户点一次节点追问，刚剥掉的假页码就回来了。

并行方案的唯一硬约束

finally 里取消产物分支时，只能 contextlib.suppress(asyncio.CancelledError)。

若有人改成 except Exception，CancelledError 不会被捕获 （它继承自 BaseException），「子任务被取消」会静默失效——断连后继续烧 token，而且没有任何报错。

另外 await task 之前必须先 add_done_callback(_reap_task)， 否则退出时会打 Task exception was never retrieved。这两条是并行方案成立的前提，不是实现细节。

完整实施记录：docs/IMPL-NOTES.md E12 · 实测数据：docs/increments/latency-profile.md、 flash-quality.md、fork-mode-ab.md

四个关键取舍

选择放弃了什么换来了什么
前端渲染，服务端不渲染视频 无法生成高保真预渲染视频（如 Manim 电影级动画） 毫秒级出图、可交互、无沙盒执行风险、服务器成本极低
SQLite 默认而非 PostgreSQL 无法水平扩展、并发写入弱 零依赖开箱即跑；DATABASE_URL 一行切换生产配置
内存向量检索而非 Milvus/Qdrant 全库上千 chunk 时要全表扫描 不用维护独立集群；千级 chunk 量级下暴力检索完全够快
实词命中率判定而非纯语义分数 需要维护停用词表，换语言/学科要重标阈值 无关问题不会被误判成"课本有覆盖"，且判定可解释

模块边界与依赖方向

依赖只能单向流动，不能反向：

api/  ──→  services/  ──→  db/  ──→  models
  │            │
  │            └──→  schemas/  （契约，谁都可以依赖）
  │
  └──→  schemas/

// 禁止：services 导入 api（服务层不该知道 HTTP 的存在）
// 禁止：db 导入 services（数据层不该知道业务）

三条硬约束

  1. 业务代码不出现 if is_postgres 分支。 双模式通过 EmbeddingStore 协议 + 工厂函数隔离，不是靠 if 判断。
  2. 确定性红线。mock_generator 和 embedding 里禁止 random / uuid4 / time / 内置 hash() （后者受 PYTHONHASHSEED 影响，进程重启就变）。统一用 hashlib.blake2b。
  3. 错误码单一来源。errors.py 定义一次，前端 api/client.ts 镜像同一份字面量。 前后端拼错一个码会静默失败，极难排查。
