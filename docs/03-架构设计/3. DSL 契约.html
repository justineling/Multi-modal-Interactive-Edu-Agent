为什么是 JSON 而不是代码

维度LLM 直接写渲染代码LLM 填 JSON（本项目）
一次成功率约 20%（Three.js 场景穿模、材质丢失、语法错误）约 100%（结构错了 Pydantic 直接拒绝）
出图耗时服务端渲染 30~60 秒前端毫秒级
可交互性视频无法交互每个元素是 React 组件，可点击、可 hover、可锚定
安全性需沙盒执行任意代码只解析数据，无代码执行
可增量修改几乎不可能（要改源码）JSON Pointer 定位 + 局部替换

代价是契约必须设计得足够有表达力。这是本项目最需要小心维护的部分—— 新增字段要考虑向后兼容，改字段名等于破坏前后端契约。

SlideDeckSpec（PPT）

class SlideDeckSpec(BaseModel):
    type: Literal["ppt"] = "ppt"      # 判别字段
    topic: str
    slides: list[SlideNode]

class SlideNode(BaseModel):
    node_id: str                    # "slide-1"，用于锚点定位
    layout: Literal["title_hero", "bullet_points", "comparison",
                    "timeline", "cause_effect", "quiz"]
    title: str
    subtitle: str | None
    bullets: list[str]                                  # 恒为数组，不返回 null
    comparison_left: list[str] | None
    comparison_right: list[str] | None
    timeline_items: list[TimelineItem] | None           # 扩展字段
    quiz_questions: list[QuizQuestion] | None           # 扩展字段
    speaker_notes: str                                  # 口语化讲解，别浪费
    source_ref: str                                     # "Bab 4.1, p.94"

6 种布局与所需字段的对应

layout必填字段渲染效果
title_herotitle + subtitle大标题页，留白足
bullet_pointsbullets要点列表，带序号
comparisoncomparison_left + comparison_right左右两栏对照
timelinetimeline_items横向时间轴，节点带页码
cause_effectbullets（作为因果链节点）箭头连接「因 → 果」
quizquiz_questions题干 + 选项，点选后显形答案

字段与布局不匹配时渲染器必须降级，不能白屏。 比如 layout: "comparison" 但 comparison_left 是 null，应该回退成 bullet_points 的样子， 而不是抛异常。每个布局组件都要有这种兜底。

Keyframe2DSpec（2D 动画）

class Keyframe2DSpec(BaseModel):
    type: Literal["anim_2d"] = "anim_2d"
    title: str
    steps: list[KeyframeStep]

class KeyframeStep(BaseModel):
    step_index: int
    narration: str                     # 当前步骤的旁白
    source_ref: str
    entities: list[Entity2D]           # 当前步骤所有元素的状态

class Entity2D(BaseModel):
    id: str                            # 注意是 id，不是 node_id
    shape: Literal["circle", "rect", "arrow", "label_box", "zone"]
    label: str
    x: float                           # 归一化 0~1000，不是像素
    y: float                           # 归一化 0~600
    color: str                         # 必须取自调色板
    details: str                       # 点击弹出的详细解释
    source_page: int | None            # 扩展字段

两个关键约定

坐标归一化
固定 0~1000 × 0~600 的逻辑坐标系，前端按容器实际尺寸等比缩放。这样同一份 AST 在任何屏幕尺寸下都正确
补间由前端做
关键帧只描述"某个步骤时元素在哪"，中间的过渡动画由 GSAP 计算。所以不需要为每一帧都生成数据

为什么不用像素？因为画布尺寸随窗口变化。用归一化坐标，同一个 spec 在手机和大屏上都能正确布局， 不需要重新生成。

SceneGraph3DSpec（3D 场景）

class SceneGraph3DSpec(BaseModel):
    type: Literal["scene_3d"] = "scene_3d"
    title: str
    nodes: list[Node3D]
    camera_tour: list[CameraPreset]    # 预设导览机位

class Node3D(BaseModel):
    id: str
    primitive: Literal["box", "sphere", "cylinder",
                       "cone", "terrain_plane", "arrow_link"]
    label: str
    position: tuple[float, float, float]     # 3 元元组，不是数组
    scale: tuple[float, float, float]
    rotation: tuple[float, float, float]     # 扩展字段
    color: str
    annotation_markdown: str                 # 悬浮标注内容
    parent_id: str | None                    # 扩展：父子层级
    source_page: int | None

class CameraPreset(BaseModel):
    name: str
    position: tuple[float, float, float]
    target: tuple[float, float, float]
    explanation: str

6 种图元

primitive对应几何典型用途
box立方体建筑、墙体、箱子
sphere球体天体、原子、圆顶
cylinder圆柱柱子、管道、炮管
cone圆锥塔尖、山峰、箭头锥体
terrain_plane平面地形地面、战场、地形起伏
arrow_link连接箭头表示"通向""属于""影响"

position 必须是 3 元元组。TS 侧要写 [number, number, number]， 不能写 number[]——后者类型不报错但运行时 R3F 拿不到完整坐标，几何体直接消失。

Pydantic → TypeScript 的四条铁律

后端 Python 定义、前端 TS 手写对应接口（不用 codegen，因为字段不多且手写更可控）。四条规则必须遵守：

#规则违反后果
1 可选字段写 T | null，不写 T? 后端恒返回 null 而不是省略字段。用 ? 会导致运行时到处 undefined，渲染器崩
2 三元组写元组类型 [number,number,number] 写 number[] 类型不报错但运行时坐标不全
3 全链路 snake_case，不做 camelCase 转换 加转换层会引入一类"字段名对不上但编译通过"的 bug
4 用 spec.type 做判别联合，禁止 any 承接 丢类型安全，IDE 无法提示，重构时全靠 grep

模型字段名容易写成
SlideNode / Node3Dnode_idid
Entity2Didnode_id
TocNodestart_page / end_pagepage_start / page_end
ChunkOutpage_start / page_endstart_page / end_page
ArtifactOutspecspec_json（那是数据库列名）

目录树和切片的页码字段命名是反的（start_page vs page_start）， 这是历史遗留。写错不会报错，只会让"点目录树定位页码"静默失效——最难排查的一类 bug。

校验与注入防护

Pydantic 强校验

所有 AST 都继承一个基类，带 extra="forbid"（多余字段直接拒绝）和递归的字符串扫描：

class AstModel(BaseModel):
    model_config = ConfigDict(extra="forbid")

    @model_validator(mode="after")
    def _reject_markup(self):
        # 递归扫所有字符串值（含 dict 的键）
        # 命中 <script / <html / <div / <style / onerror= / javascript: /
        #      function( / (=> / import / three.  任一即抛错

为什么要在契约层拦 HTML/JS？因为 spec 会被前端直接渲染。如果模型输出里混进 <script> 或 onerror=，就是 XSS 风险。这道闸门在数据入口就掐死， 比在前端做转义更可靠。

校验失败怎么办

LLM 输出 JSON
可能带 ```json 围栏、前后噪声
↓
抽取 + Pydantic 校验
失败 → 把错误信息回灌给模型重试
↓ 最多 3 次

保证用户永远能拿到产物，不会空手

重试期间会发 error 事件（retryable: true），但不中断流。 用户会看到一条提示，然后继续等结果。

怎么安全地扩展契约

假设你要加一个"图片分栏"布局。按这个顺序改，缺一步就会出问题：

  1. 后端加字段（只加可选字段）

    schemas/artifacts.py 里给 SlideNode 加 image_ref: str | None = None， 并在 layout 的 Literal 里加 "image_split"。

    绝不能改已有字段名或类型——那会破坏所有已落库的历史 spec。

  2. 前端 TS 同步

    types/artifact.ts 加 image_ref: string | null， SlideLayout 联合类型加 "image_split"。

  3. 写渲染器并注册

    新建 layouts/ImageSplitLayout.tsx，在 slideLayouts.tsx 的 LAYOUT_REGISTRY 里注册。策略分发靠这个注册表，漏了就是空白页。

  4. 让 mock 生成器能产出

    mock_generator.py 里加上这个布局的确定性生成逻辑，否则演示模式下永远看不到它。

  5. 补测试

    契约正反例（test_contracts.py）、渲染冒烟（SlideRenderer.test.tsx）、 mock 确定性（test_mock_determinism.py）。

只加不改。契约演进唯一安全的策略是"新增可选字段 + 新 literal 值"。 一旦改了已有字段的名字或语义，所有历史版本的 spec 都会失效，而版本历史是 append-only 的， 你没法批量迁移。
