表关系总览

workspaces ──┬── documents ──┬── document_chunks ── chunk_vectors
             │               │      (1:N)              (1:1)
             │               └── (toc_tree 存 JSON)
             │
             ├── artifacts ────── artifact_versions
             │      (1:N)              (1:N, append-only)
             │
             └── messages
                    (会话历史，供刷新恢复)

所有子表都带 workspace_id 并 ON DELETE CASCADE。 删一个工作区，它的文档、切片、向量、产物、消息全部连带删除。

七张表逐一看

1. workspaces — 对话工作区

字段类型说明
idString(36)UUID 主键
titleString(255)工作区名称
created_atDateTime创建时间
last_active_atDateTime最近活动时间，列表按它倒序

隔离边界。所有检索都强制带 workspace_id 过滤。 同一个 PDF 传到两个工作区，切片 chunk_id 集合零交集——这是 P0-01 的硬验收。

2. documents — 上传的文件

字段类型说明
idString(36)主键
workspace_idFK所属工作区
filenameString(255)原始文件名
stored_pathString(512)磁盘路径（可为空，如体检失败未落盘）
page_countInteger页数
statusString(20)pending / parsing / ready / failed / cancelled
progressInteger0~100，解析中每 0.3 秒更新
error_code / error_messageString / Text失败时的错误码与中文提示
toc_treeJSON目录树，结构 [{code, title, level, start_page, end_page, children}]
parser_modeString(20)解析模式（如 page_fallback 表示按页兜底）

toc_tree 里的字段是 start_page / end_page， 而 document_chunks 里是 page_start / page_end。 两套命名不一致是历史遗留，前端 TS 类型必须按实际字段写，写错会导致目录树点击定位静默失效。

3. document_chunks — 结构化切片

字段类型说明
idString(36)主键
document_id / workspace_idFK双外键，便于按工作区直接检索
section_codeString(50)章节号，恒非空（识别失败时填 P0001 这样的伪章节）
section_titleString(255)章节标题
levelInteger层级 1~4
chunk_indexInteger全局连续序号，用于稳定排序
page_start / page_endInteger1 基闭区间，可回溯到真实页码
contentText切片正文
char_lenInteger字数，用于碎块合并判断

两个索引：(workspace_id, section_code) 用于章节精确过滤， (document_id, chunk_index) 用于稳定排序。

4. chunk_vectors — 向量（独立表）

字段类型说明
chunk_idFK唯一约束 uq_vec_chunk，一个切片一条向量
workspace_id / document_idString(36)冗余存储，避免检索时 JOIN
dimInteger维度，默认 1536
vectorTextSQLite 模式存 JSON 数组；PG 模式映射 vector(1536)
modelString(80)产生该向量的模型标识，便于换模型时区分

5. artifacts — 产物（指向最新版本）

字段类型说明
idString(36)主键
titleString(255)产物标题
artifact_typeString(20)ppt / anim_2d / scene_3d
versionInteger当前最新版本号，每次 patch +1
spec_jsonJSON当前最新版本的完整 AST
anchor_sectionString(50)生成时锚定的章节，用于后续追问的范围推断

6. artifact_versions — 版本历史（append-only）

字段类型说明
artifact_idFK所属产物
versionInteger版本号，与 artifact_id 组成唯一约束
spec_jsonJSON该版本的完整快照（deepcopy，不与 artifacts 共享对象）
patch_opsJSON产生该版本所用的补丁指令（v1 为 null）
origin_turn_idString(36)来源回合 ID，可追溯到哪次对话

7. messages — 会话历史

字段类型说明
roleString(16)user / assistant
content_markdownText消息正文
knowledge_scopeString(24)syllabus_strict / hybrid_extended
citationsJSON[{label, section_code, page_start, page_end}]
anchorJSON该轮携带的锚点（可为 null），刷新恢复时还原
artifact_id / artifact_versionString / Integer关联产物
demo_modeBool该轮是否演示模式产出，可追溯

为什么版本表是 append-only

这是整个数据模型里最重要的一个设计。看这段逻辑：

patch 一次时发生什么：

1. artifact.spec_json  ← 新的完整 AST（当前版本）
2. INSERT artifact_versions (version=N+1, spec_json=新快照, patch_ops=本次ops)

// 注意：绝不 UPDATE 任何已有的 version 行
设计好处
artifacts 只存最新读最新版本不用扫历史表，一次查询
versions 只追加历史永不丢失，可随时回看任意版本
每个版本存完整快照回看时不用重放补丁链，直接读

代价是存储冗余（20 个版本 ≈ 20 份 AST）。但 AST 是纯 JSON，几 KB 到几十 KB， 20 个版本也就几百 KB，换来的是"回看零成本"和"历史不可篡改"。

写快照必须 copy.deepcopy。 SQLAlchemy 的 JSON 类型不追踪嵌套结构的原地修改。 如果 artifact.spec_json 和新版本行的 spec_json 是同一个 dict 对象， 后续对 artifact 的原地修改会同时改到历史行的内存对象，一旦该行因别的原因 flush，脏数据就写回历史了。

回归测试用对象身份断言锁死：version_row.spec_json is not artifact.spec_json。换浅拷贝立刻红。

dual-mode 兼容怎么做到

同一套 models.py 同时跑 SQLite 和 PostgreSQL，靠三件事：

问题做法
UUID 类型统一用 String(36) + Python 侧 uuid4().hex 生成，不用 PG 的 UUID 类型
JSON 类型用 SQLAlchemy 通用 JSON，SQLite 存 TEXT，PG 存 JSONB
向量类型不用数据库原生向量列，统一存 Text（JSON 数组），检索在 Python 侧算余弦

向量这一步是关键取舍：放弃 pgvector 的索引加速，换来"业务代码完全不感知数据库类型"。 千级 chunk 量级下，Python 侧暴力余弦完全够快（实测全库检索毫秒级）。

向量存储的协议抽象

# db/vector_store.py
class EmbeddingStore(Protocol):
    async def upsert_vectors(...)      # 写入/覆盖
    async def search_similar(...)       # 余弦检索
    async def delete_by_document(...)   # 删文档时清理

# 工厂按 DATABASE_URL 返回不同实现
def build_vector_store() -> EmbeddingStore:
    if url.startswith("postgresql"): return PgVectorStore(...)
    return MemoryVectorStore(...)

业务代码里不允许出现 if is_postgres。 判断只允许出现在这个工厂函数里，其他地方一律面向 EmbeddingStore 协议编程。 验收时会 grep -r "is_postgres" backend/app，必须零结果。

两个容易踩的坑

坑一：SQLite 相对路径锚定

DATABASE_URL 默认是 sqlite+aiosqlite:///./data/app.db，相对路径锚定在 backend/。 如果你有时用 uvicorn --app-dir backend（工作目录是项目根），有时 cd backend && uvicorn， 会落到两个不同的 db 文件，表现为"上传过的 PDF 重启后消失"。

坑二：WAL 伴生文件

SQLite 开启 WAL 模式后会生成 app.db-wal 和 app.db-shm。 .gitignore 必须包含这三个模式（*.db / *.db-wal / *.db-shm）， 否则伴生文件会被误提交进仓库。
