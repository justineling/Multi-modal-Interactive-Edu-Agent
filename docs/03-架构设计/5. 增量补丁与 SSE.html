5增量补丁与 SSE

两个协议层设计：怎么只改一处而不动其他（补丁），怎么把生成过程实时推给前端（SSE）。这两块是前后端协作最容易出问题的地方。

PatchOp 五种操作

class PatchOp(BaseModel):
    op: Literal["update_node", "insert_node", "delete_node",
                "replace_subtree", "focus_camera"]
    node_path: str          # JSON Pointer 风格
    payload: dict | None    # 局部字段，不是整树
    reason: str
opnode_path 指向payload前端如何应用
update_node 已存在的元素，如 /slides/2 局部字段 dict 字段级 merge：{...current, ...payload}
insert_node 父列表 + 插入位，如 /slides/3（插到索引 3 前） 完整新节点 整体插入
delete_node 待删元素 必须为 null 整体移除
replace_subtree 任意单节点路径 完整子树 整体替换（仅用户明确要求"整块重做"时用）
focus_camera /camera_tour/{i} {"preset_name": "..."} 不写入 spec，走旁路设置相机

node_path 的语义

路径必须匹配这个正则（在 Pydantic 层强制校验）：

^/(slides|nodes|steps|camera_tour)(/\d+)?(/(entities)(/\d+)?)?$
合法路径指向
/slides/2PPT 第 3 页（索引 2）
/nodes/53D 场景第 6 个节点
/steps/12D 动画第 2 个关键帧
/steps/1/entities/3第 2 帧里的第 4 个元素
/camera_tour/0第 1 个预设机位
/slides整个 slides 列表（只能用于 insert/delete 的父层声明）

非法路径（//slides/2、/slides/abc、/slides/-1、超深路径）返回 PATCH_PATH_INVALID。

replace_subtree 只支持单节点路径。因为 payload 类型是 dict， 承载不了整个列表。/slides 这种列表路径会返回 PATCH_PATH_INVALID， 提示改用 insert_node + delete_node 组合。

最容易写错的一点：字段级 merge

update_node 的 payload 只包含被修改的字段，必须做字段级 merge。 整体替换会让节点直接崩掉。

真实数据长什么样

用户点第 3 页追问后，后端返回的 payload 实测只有两个字段：

{
  "op": "update_node",
  "node_path": "/slides/2",
  "payload": {
    "bullets": ["4.1.3 公民权条件", "..."],
    "speaker_notes": "..."
  }
}

而 SlideNode 有 11 个字段。另外 9 个（node_id、layout、title、 subtitle、source_ref…）一个都不带。

写错的后果

// ❌ 错误：整体替换
setAtPath(spec, "/slides/2", payload)
// 结果：{bullets, speaker_notes}  ← layout 变成 undefined
//       LAYOUT_REGISTRY[undefined] 拿不到布局 → 渲染器当场崩溃

// ✅ 正确：字段级 merge
setAtPath(spec, "/slides/2", { ...current, ...payload })
// 结果：11 个字段都在，只有 bullets 和 speaker_notes 变了

各 op 的正确语义汇总

op语义
update_nodemerge（不是替换）
insert_node整体插入新节点
replace_subtree整体替换
delete_node整体移除
focus_camera不写 spec，旁路

后端执行器：deepcopy + 定点写入

def apply_patch(spec_dict, ops):
    working = copy.deepcopy(spec_dict)        # ① 深拷贝

    for op in ops:
        resolve(working, op.node_path)        # ② 定点写入
        apply_op(working, op)

    model = parse_spec(working)               # ③ Pydantic 强校验
    if model is None:                            # 失败则整批回滚
        raise AppError(CONTRACT_VALIDATION_FAILED)

    return working, model, changed_paths

三条禁止事项

① 禁止 Model(**new_dict) 重建对象。Pydantic 会规范化字段顺序和数值表示，键序一变， "字节级不变"的断言就挂了。

② 禁止 model_copy(update=...) 后整体 dump。同上。

③ 禁止"删掉再插回"同位置元素。键序会变，而且索引会平移。

正确做法是在深拷贝出的 dict 上原地定点写入，保持所有未触及部分的键序和值表示完全不变。

整批回滚

所有写入只发生在 working（深拷贝）上。任何一步抛错就丢弃 working， 原始 dict 一字不动。所以一批 20 个 op 里第 15 个失败，前 14 个也不会生效。

指纹自检：怎么证明"其他没变"

验收标准是「patch 后 AST 差异仅限被锚定节点的子树，其余节点字节级不变」。 怎么自动化验证这个？用全路径指纹表：

def path_fingerprints(obj, prefix="") -> dict[str, str]:
    # 递归遍历，每个路径生成 sha256
    # "/slides/0" → "a3f2..."
    # "/slides/0/title" → "b8c1..."
    # ...

before = path_fingerprints(original)
after  = path_fingerprints(patched)

# 剔除 changed_paths 及其祖先/后代后，两表必须完全相等
assert without_changed(before, changed_paths) == without_changed(after, changed_paths)

三个实现细节

细节原因
序列化用 sort_keys=True 否则同样的 dict 因插入顺序不同会算出不同指纹
祖先判断必须用 / 边界 裸 startswith 会把 /slides/1 当成 /slides/10 的祖先，产生假阳性
insert/delete 的 changed_paths 声明到父列表层 下标平移会让后续所有兄弟节点的"路径内容"变了。声明到元素层会让断言永远失败

指纹只能同语言侧自比较，严禁跨语言比对。 Python json.dumps(1.0) 是 "1.0"，JS JSON.stringify(1.0) 是 "1"。 前后端一致性靠字段级对应表 + Pydantic 校验保证，不靠指纹。

一条假阳性的教训

曾经有一次测试报告"历史版本被后续 patch 改写"，看起来像严重缺陷。实际原因是： 测试的 original 取自 SSE 事件（键排序），v1 取自 REST 接口（库内插入序）， 用保留键序的方式比对，纯键序差异被报成了内容改写。

断言"内容被改写"必须区分「值不等」与「字节表示不等」。 用保留键序的字节比对去断言语义等值 → 假阳性； 反过来用 sort_keys 比对去断言"字节级不变" → 漏掉真实键序变化。 两种断言各有适用场景，选错方向就会误报或漏报。

乐观锁与并发冲突

两个标签页同时基于 v1 提交补丁，会怎样？

class PatchRequest(BaseModel):
    artifact_id: str
    base_version: int          # 客户端认为的当前版本
    ops: list[PatchOp]         # 1~20 个

# 服务端检查：
if request.base_version != artifact.version:
    raise AppError(PATCH_BASE_VERSION_CONFLICT)   # HTTP 409

这是"读 → 比 → 写"，理论上两个请求可能同时通过比较。所以还有第二道防线： (artifact_id, version) 的唯一约束。第二个写入会撞约束，捕获 IntegrityError 后翻译成同样的 409。

数据不会坏（约束兜住了），但必须给用户明确提示「画布已被其他操作更新，请刷新」， 而不是抛 500。

SSE 八类事件协议

端点：POST /api/chat/stream，Content-Type: text/event-stream。

event触发时机关键字段
turn_start流开始turn_id / demo_mode / has_anchor / mode
retrieval检索与评估完成grader_status / section_scope / top_score / chunks
token文本增量（可多次）delta
modality_decision路由完成artifact_type / action / reason / user_override
artifactAST 就绪create：spec + version；patch：ops + base_version
citations引用汇总[{label, section_code, page_start, page_end}]
error任一阶段失败code / stage / retryable / attempt
turn_end流结束（必发）duration_ms / ttft_ms / version

五条硬规则

  1. data: 必须是单行紧凑 JSON（无换行）。
  2. 事件顺序固定：turn_start → retrieval → modality_decision → token* → artifact? → citations → turn_end。
  3. error 可插入任意位置，但之后仍必须补发 turn_end。
  4. 每 15 秒无事件时发 : ping 注释行保活（防止中间层断开空闲连接）。
  5. 无 API Key 时 demo_mode: true 必须在 turn_start 和 turn_end 两处都携带。

为什么 turn_end 必发？前端收到它才会结束"流式态"、解除输入框禁用。 如果异常路径漏发，用户界面会永远卡在"生成中"，只能刷新页面。

前端为什么必须手写解析器

不能用 EventSource。它不支持 POST 请求，不能带自定义 header， 而我们的对话是 POST + JSON body。

必须用 fetch + ReadableStream 手动解析：

const res = await fetch("/api/chat/stream", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
  signal: abortController.signal,
});

const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  buffer += decoder.decode(value, { stream: true });

  // 按 \n\n 切事件块，注意最后一块可能不完整，要留在 buffer 里
  const blocks = buffer.split("\n\n");
  buffer = blocks.pop() ?? "";

  for (const block of blocks) {
    // 解析 event: / data: 行，忽略 ": ping" 注释
    // 多个 data: 行要用 \n 拼接（SSE 规范）
  }
}

五个必须处理的细节

细节不处理会怎样
跨 chunk 的半截事件网络分片会把一个事件切成两半，JSON.parse 直接抛错
: ping 注释行当成事件解析失败
多 data: 行拼接后端目前是单行，但按规范必须支持，防御未来变更
收到 turn_end 即主动结束不依赖服务端关连接，否则服务端不关就一直等
AbortSignal 取消切换工作区或组件卸载时，旧流还在跑，会串到新会话里

React StrictMode 在开发模式下 effect 会跑两遍。 如果 useChatStream 不做幂等守卫（AbortController + in-flight ref）， 一次提问会发两条 SSE 请求。这是开发环境专属的坑，生产不会出现，但调试时很困惑。
