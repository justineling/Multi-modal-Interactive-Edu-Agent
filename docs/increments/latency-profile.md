## 二、分段耗时分解

### 2.1 事件边界法（用户视角，3 次中位数）

| # | 阶段 | 中位数 (ms) | 最小 | 最大 | 占比 |
|---|---|---:|---:|---:|---:|
| 1 | 检索 + 相关性评估 | **5.8** | 5.3 | 7.9 | 0.01% |
| 2 | 形态路由 | **0.0** | 0.0 | 0.1 | 0.00% |
| 3 | 正文流式输出 | **10,781.3** | 9,391.9 | 13,332.4 | **16.3%** |
| 4 | **产物生成（`complete_json`）** | **55,490.8** | 44,109.7 | 64,293.4 | **83.7%** |
| 5 | 引用汇总 + 后校验 | **0.2** | 0.1 | 0.3 | 0.00% |
| 6 | 落库 + 收尾 | **6.8** | 6.3 | 7.9 | 0.01% |
| | **合计** | **66,284.6** | 53,514.0 | 77,642.0 | 100% |
| | （其中 TTFT，累计到首个 token） | **4,615.6** | 3,749.9 | 5,202.0 | — |

单次明细：

| 次 | 总耗时 | TTFT | 阶段3 正文 | 阶段4 产物 |
|---|---:|---:|---:|---:|
| 1 | 77,642.0 | 5,202.0 | 13,332.4 | 64,293.4 |
| 2 | 66,284.6 | 3,749.9 | 10,781.3 | 55,490.8 |
| 3 | 53,514.0 | 4,615.6 | 9,391.9 | 44,109.7 |

**读数**：
- 阶段 1/2/5/6 加起来不到 **14 毫秒**，与 66 秒无关。**检索里没有 LLM 调用**（`_retrieve` 走本地哈希向量 + 纯 Python BM25 + 规则打分），`route()` 是纯函数。这一条可以彻底排除「检索拖慢」的怀疑。
- 阶段 3 的正文流式（`deepseek-flash`）10.8 秒里，TTFT 占 4.6 秒，剩余 6.2 秒是输出 1570~2795 字符的正文。
- 阶段 4 就是全部问题。见第三节。

### 2.2 方法跨度法（服务端视角，交叉校验）

| 方法 | 中位数 (ms) | 最小 | 最大 |
|---|---:|---:|---:|
| `_retrieve` | 5.7 | 5.2 | 7.8 |
| `route` | 0.0 | 0.0 | 0.0 |
| `_build_context` | 0.1 | 0.1 | 0.1 |
| `_reply_stream` | 10,788.4 | 9,398.6 | 13,340.8 |
| `_create_artifact_stream` | 55,483.6 | 44,102.9 | 64,284.8 |
| ├ `_generate_spec_stream` | 55,478.7 | 44,098.5 | 64,276.5 |
| └ `LLMClient.complete_json` | 55,478.2 | 44,098.2 | 64,275.9 |
| `_build_citations` | 0.1 | 0.1 | 0.1 |
| `_drop_invalid_citations` | 0.0 | 0.0 | 0.1 |
| `_persist_turn` | 6.6 | 6.3 | 7.9 |

两套时钟吻合到 **10 毫秒以内**（如 55,483.6 vs 55,490.8），说明异步生成器缓冲带来的偏差可以忽略。

**关键比值**：`_create_artifact_stream` 55,483.6ms 中 `complete_json` 占 55,478.2ms —— **99.99%**。
产物阶段没有隐藏开销：没有排队、没有落库等待、没有额外的重试包装，就是一次干净的模型调用。

### 2.3 patch 回合（锚点追问）基线

同一份产物上点 `/slides/1` 追问「这一页的要点拆细一点，并说明对普通人的影响」，跑 1 次：

| # | 阶段 | 耗时 (ms) |
|---|---|---:|
| 1 | 检索 + 相关性评估 | 97.3 |
| 2 | 形态路由 | 0.1 |
| 3 | 正文流式输出 | 5,180.8 |
| 4 | 产物生成（`complete_json` 出 ops） | 21,534.2 |
| 5 | 引用汇总 + 后校验 | 0.2 |
| 6 | 落库 + 收尾 | 12.8 |
| | **合计** | **26,825**（TTFT 3,256） |

**patch / create = 26,825 / 66,285 = 40.5%**，满足 P0-10③「≤ 同规模全量生成的 50%」。
原因很直白：ops 的输出量（一个节点几个字段）远小于 5 页完整 spec，所以推理与生成都短得多。

> 阶段 1 的 97.3ms 是**冷启动**造成的（`MemoryVectorStore` 首次检索要从库里把 65 条向量读进内存），
> 不是每次回合的真实成本。3 次基线回合里该阶段只有 5.3~7.9ms，因为入库时已经把向量灌进了内存。

## 三、第 4 阶段参数级明细

### 3.1 调用参数（`LLMClient.complete_json` 实际发出的 payload）

| 参数 | 值 | 备注 |
|---|---|---|
| `model` | `deepseek-v4-pro` | 取 `LLM_MODEL_GENERATOR` |
| `temperature` | `0.2` | 代码默认值 |
| `max_tokens` | **未传（None）** | 输出长度完全不受限，由模型自己决定何时停 |
| `response_format` | `{"type":"json_object"}` | 已启用 |
| `stream` | 未传（即非流式） | 意味着**必须等整份 JSON 生成完才拿到第一个字节** |
| 超时 | `LLM_TIMEOUT_SECONDS=60`（生产） | 剖析时临时 300s |
| 传输层重试 | 最多 3 次（`RETRY_BACKOFF = 0/0.4/1.0s`） | 本次 3 次运行**一次都没触发** |
| 契约重试 | `_generate_spec_stream` 最多 3 次 | 本次 3 次运行 **`contract_retry = 0`**，每次只调用 1 次 |

三次运行的实际调用：

| 次 | 模型 | 提示词字符 | `max_tokens` | `temperature` | 耗时 (ms) | prompt_tokens | completion_tokens |
|---|---|---:|---|---|---:|---:|---:|
| 1 | deepseek-v4-pro | 1,999 | None | 0.2 | 64,275.6 | 1,005 | 5,736 |
| 2 | deepseek-v4-pro | 1,999 | None | 0.2 | 55,478.0 | 1,005 | 4,979 |
| 3 | deepseek-v4-pro | 1,999 | None | 0.2 | 44,098.0 | 1,005 | 3,676 |

**`contract_retry` 全程 0 次**，所以「重试翻倍」在当前配置下**不是**瓶颈（IMPL-NOTES E11 修好之后
一次过）。但只要加 `max_tokens` 截断或换更弱的模型，这个前提就会变 —— 见第五节风险分析。

### 3.2 输入提示词构成（1,999 字符 / 1,005 tokens）

| 组成 | 字符数 | 占提示词 |
|---|---:|---:|
| System prompt（`_ARTIFACT_SYSTEM_PROMPT`） | 242 | 12.1% |
| User 段中的 `_ARTIFACT_CONTRACT["ppt"]` 契约原文 | **1,395** | **69.8%** |
| User 段的头部说明（321）+ 8 条课本事实 + 尾部指令（约 41） | 362 | 18.1% |
| **合计** | **1,999** | 100% |

> 8 条「课本事实」里混进了 `- 4.1.2 Kuasa Sultan`（一个章节标题）和两条被 `_clip(…, 110)` 截断的
> 半句（`宪法文本里的每一处措辞变化，背后都`）。这属于 `mock_generator.extract_facts` 的抽取质量问题，
> 与本次耗时测量无关，但会同时影响契约命中率 —— 记在这里备查。

> 契约占了提示词的 **七成**。直觉上「提示词太长拖慢首字」，但实测**否掉了这个直觉**：
> 响应头 TTFB 只有 **243~535 毫秒**，`prompt_tokens` 仅 **1,005**。真正慢的是模型在吐出第一个
> 内容 token 之前先做了 **36~54 秒的内部推理**（见 3.3）。把契约砍一半省不到 0.5 秒。

### 3.3 网络耗时 vs 模型耗时（流式探针分离）

非流式调用只能测到「整段返回」一个时间点，无法拆开。用同一份提示词加 `stream=True` 重放，
每个 SSE chunk 都带时间戳，于是可以分开：

| 实验 | 样本 | 响应头 TTFB | 首内容 token | 其中「思考」 | 内容生成 | 总耗时 | completion_tokens | 输出页数 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| v4-pro 默认 effort | 1 | 243.3 | 45,830.0 | 未测 | 11,594.2 | 57,435.3 | 4,851 | 5 |
| v4-pro 默认 effort | 2 | 518.9 | 37,168.8 | **35,991.0** | 5,334.3 | 42,511.3 | 3,961 | 5 |
| v4-pro 默认 effort | 3 | 489.3 | 55,046.8 | **53,940.2** | 8,884.9 | 63,950.7 | 6,067 | 6 |

（单位 ms。第 1 次探针跑在旧版脚本上，没有采集 `reasoning_content`，所以「思考」列为空。）

**决定性证据**：DeepSeek V4 系列会把内部推理走独立的 `delta.reasoning_content` 字段。探针直接
计量了这个字段：

- 第 2 次：思考 **35,991ms / 6,782 字符 / 3,172 chunk**，之后才出现第一个 `content` token
- 第 3 次：思考 **53,940ms / 10,006 字符 / 4,697 chunk**

**结论：产物调用的 85%~88% 时间花在「模型思考」上，而不是网络、不是预填充、不是 JSON 序列化。**
网络与排队（响应头 TTFB）只占 0.2~0.5 秒。

一个额外的交叉证据：正文流式的提示词长度是 1,819 字符（system 89 + user 1,730），与产物提示词
1,999 字符几乎一样大，但首字只要 **3.7~5.2 秒**。同样的提示词规模，换成 flash 就快一个数量级 ——
**瓶颈是模型档位 + 推理开销，不是输入长度**。

### 3.4 输出规模

| 次 | 产物页数 | spec JSON 字符数 | completion_tokens |
|---|---:|---:|---:|
| 1 | 7 | 2,847 | 5,736 |
| 2 | 5 | 2,464 | 4,979 |
| 3 | 5 | 2,154 | 3,676 |

`completion_tokens`（3,676~5,736）明显高于可见输出字符所能解释的量（2,154~2,847 字符 ≈ 1,200~1,800
token），差额约 2,500~4,000 token 全部是 3.3 节计量到的推理 token。

3 次基线产物均为 5~7 页、`layout` 覆盖 `title_hero / bullet_points / comparison / cause_effect / quiz`
五种，`source_ref` 页码落在检索区间 `p.71-77` 内（其中一次只写了 `4.1.2` 未带 `p.N`，属质量瑕疵，
见第七节）。

## 四、三个假设的验证结论

### 假设 A：正文流式与产物生成是串行的 —— ✅ **成立**

代码层面：`stream_turn` 第 338 行 `async for delta in self._reply_stream(...)` 完整跑完，
第 364 行才开始 `async for event in self._create_artifact_stream(...)`。

实测（方法跨度法，3 次）：

| 次 | 正文 span | 产物 span | 间隙 |
|---|---|---|---|
| 1 | 8 → 13,349ms（13,341ms） | 13,349 → 77,634ms（64,285ms） | **+0ms** |
| 2 | 6 → 10,794ms（10,788ms） | 10,794 → 66,278ms（55,484ms） | **+0ms** |
| 3 | 6 → 9,405ms（9,399ms） | 9,405 → 53,508ms（44,103ms） | **+0ms** |

三次间隙都是 **0 毫秒**，完全串行。

**产物是否依赖正文内容？不依赖。** 读代码确认：

```python
async def _create_artifact_stream(self, req, decision, context, result):
```

签名里**没有 `reply` 参数**。它的提示词由 `_artifact_prompt(req, decision, context)` 构造，
`context` 来自 `_build_context(req, result)`，即**只依赖检索结果**，与正文文本无关。
正文只影响 `_persist_turn` 落库和 `_drop_invalid_citations` 的页码后校验。

**并行化理论上限收益 = min(正文 10,788ms, 产物 55,484ms) = 10,788ms ≈ 整轮的 16.3%。**
即总耗时 66.3s → 55.5s。

### 假设 B：`effort` 参数能降耗 —— ❌ **不成立（实测反向）**

**当前 `complete_json` 没有传 `effort`**（payload 里不存在该字段），走的是模型默认值。
`GET /v1/models` 确认两个模型都声明了：

```json
"effort": {"supported_levels": ["low","high","max"], "default_level": "high"}
```

对照实验（同一份 1,999 字符提示词，`deepseek-v4-pro`）：

| effort | 样本 | 总耗时 | 其中思考 | completion_tokens | 页数 | 契约 |
|---|---:|---:|---:|---:|---:|---|
| 默认（high） | 57,435.3 | — | — | 4,851 | 5 | ✅ |
| 默认（high） | 42,511.3 | 35,991.0 | 3,961 | 5 | ✅ |
| 默认（high） | 63,950.7 | 53,940.2 | 6,067 | 6 | ✅ |
| **默认 中位数** | 3 | **57,435.3** | 44,965.6 | 4,851 | — | 3/3 通过 |
| `low` | 76,166.4 | — | 6,758 | 5 | ✅ |
| `low` | 57,824.3 | 49,457.4 | 5,915 | 6 | ✅ |
| **`low` 中位数** | 2 | **66,995.4** | 49,457.4 | 6,337 | — | 2/2 通过 |

**`effort=low` 被 API 正常接受（无 4xx），但没有更快，反而慢 17%。** 两个 `low` 样本的
`completion_tokens`（6,758 / 5,915）都高于默认档的三个样本（3,961 / 4,851 / 6,067），
其中唯一采集了 `reasoning_content` 的那次，思考字符数 10,590 也高于默认档的 6,782 / 10,006。
也就是说 `effort=low` 并没有压缩思考量，两个样本都指向反方向。

> 表中「思考」列：默认档 n=2（第 1 个探针跑在旧版脚本上未采集该字段），`low` 档 n=1。

诚实说明：`low` 只有 **2 个样本**，单次调用本身的方差就很大（默认档实测 42.5~64.0 秒，
跨度 50%）。所以准确表述是：**「`effort=low` 能降耗」这一假设得不到任何数据支持，且两个样本
都指向反方向**；要下定论需要 5 次以上样本，但按性价比不值得为它烧 token。

**副作用提示**：既然 `effort` 参数会改变推理长度，它就不是「免费开关」。任何把 `effort`
写进生产代码的改动都必须先有 5+ 样本的对照数据。

### 假设 C：只生成 2 页时耗时近似线性下降 —— ❌ **不成立（是次线性）**

同一份提示词，把契约里的「共 5~8 页」改成「共 2 页」并删掉「至少 3 种 layout」这条（2 页做不到），
其余不变：

| 页数 | 总耗时 | 首内容 token | 其中思考 | 内容生成 | completion_tokens |
|---|---:|---:|---:|---:|---:|
| 5 页（原始 5~8 页契约） | 57,435.3 | 45,830.0 | 未测 | 11,594.2 | 4,851 |
| **2 页** | **36,488.1** | 33,355.5 | 未测 | 3,119.0 | 3,292 |

2 页耗时是 5 页的 **63.6%**，而页数是 40%。**不是线性。**

拆开看原因很清楚：

- **思考/首字阶段**：45,830 → 33,355ms，只降 **27%**（少 12.5 秒）
- **内容生成阶段**：11,594 → 3,119ms，降 **73%**（少 8.5 秒）

也就是说，**页数只影响「写 JSON」那一段（占总时长约 20%），不影响「想清楚」那一段（占 80%）**。
这个结论直接决定了「分批下发」能拿到多少收益 —— 见第五节手段 2。

2 页产物契约校验通过，2 页 / `['title_hero','quiz']`，符合改后的契约。

## 五、候选优化手段清单（按性价比排序）

### 🥇 手段 1：产物生成换轻量模型（`deepseek-flash`）

**实测对照**（同一份 1,999 字符提示词，`deepseek-v4-pro` vs `deepseek-flash`）：

| 模型 | 样本 | 总耗时 | 首内容 token | 其中思考 | completion_tokens | 页数 | 契约 | 页码真实 |
|---|---:|---:|---:|---:|---:|---:|---|---|
| v4-pro | 3 | 57,435 / 42,511 / 63,951（中位 **57,435**） | 37,169~55,047 | 35,991~53,940 | 3,961~6,067 | 5~6 | 3/3 ✅ | ✅ |
| **flash** | 3 | 13,063 / 10,059 / 6,776（中位 **10,059**） | 926~6,104 | 0~5,234 | 1,200~2,206 | 6 | 3/3 ✅ | ✅ |

- **预期收益**：产物阶段 55,491ms → 10,059ms（中位），**整轮 66,285ms → 估算 20,900ms，降 68%**。
  算式：`66,285 − 55,491 + 10,059 = 20,853ms`。
- **风险**：
  - 样本只有 3 次，且只覆盖「5~8 页 PPT」这一种形态；`anim_2d`（8 字段 entity × 2~5 帧）、
    `scene_3d`（10 字段 node + 4 字段机位）的字段密度更高，flash 的契约一次通过率**未测**。
  - 内容深度：本次 3 次 flash 产物的 `speaker_notes` 平均 70~76 字符、内容具体（引用了「苏丹只保留
    宗教与习俗事务权限」等课本事实），**不像模板填充**；但「timeline 年份准确性」「quiz 干扰项质量」
    这类细节未逐条核对。
  - **这条推翻了 `llm_client.complete_json` docstring 里「准确率优先于延迟」的既有取舍**
    （IMPL-NOTES E11 问题 2）。要改默认值，必须先把上面两条未测项补齐。
- **对契约的影响**：**零**。契约是 `parse_artifact_spec` 的 schema 校验，与模型无关。
  唯一的隐性影响是：模型变弱 → 一次通过率可能下降 → `contract_retry` 从 0 变 1，
  而**一次重试就是一次完整调用**（flash 约 10 秒），两次就吃掉全部收益。所以必须把
  「flash 的 contract_retry 率」作为验收指标，不能只看单次耗时。

### 🥈 手段 2：分批下发（先出前 2 页，再补剩余）

- **预期收益**：
  - **首屏可见时间**（画布上出现第一批页面）：`正文 10,788 + 2 页 36,488 = 估算 47,300ms`，
    对比现在 `66,285ms` → **省 19 秒（29%）**。
  - **总耗时**：如果两批**串行**，`10.8 + 36.5 + 约 40（后 3 页）= 约 87s`，**总耗时反而变差 31%**；
    如果两批**并行**，`10.8 + max(36.5, 约 40) = 估算 51s`，省 15s。
  - 算式里的「后 3 页约 40s」是**估算**：按 2 页 36.5s、5 页 57.4s 内插，3 页约 40~45s（未测）。
- **关键前提（来自假设 C）**：页数与耗时是**次线性**关系。把 5 页拆成 2+3 两批，总 token 量不变
  但**思考开销要付两遍**，所以并行才能赚、串行一定亏。
- **风险**：
  - 跨批的 layout 多样性约束（「中间各页至少 3 种不同取值」）在单批内无法判定，需要在合并后补校验，
    不合格时只能整份重来。
  - `node_id` 需要全局重编号（`slide-1..slide-N`），批次间风格/措辞可能不一致。
  - 引用页码需跨批合并去重；`citations` 事件目前在产物之后发一次，分批后要改成多次或延后。
  - 失败语义：第一批成功、第二批失败 → 画布上是半份产物，`_persist_turn` 落库的 `artifact_version`
    指向谁？需要新定义「部分产物」状态。
- **对契约的影响**：**中等**。spec 结构本身不变（仍是完整 `slides` 数组），但需要新增「分批」的
  事件语义（多次 `artifact` 事件或新的 `artifact_chunk` 事件），前端 reducer 与
  `ARTIFACT_VERSION_KEEP` 的版本快照都要跟着改。属于「加字段」而非「改字段」，符合
  HANDOVER 第七节第 3 条「契约演进只能加不能改」。

### 🥉 手段 3：正文与产物并行

- **预期收益**：省 **10,788ms（16.3%）**，`66,285 → 55,500ms`。
  **与手段 1 叠加后收益骤降**：产物只剩 10.1s 时，正文 10.8s 反而成了较长的那条，
  并行后 `估算 max(10.8, 10.1) + 1 = 约 12s`，相比串行的 20.9s 省 9 秒。**TTFT 完全不受影响**
  （仍是检索 6ms + 首 token 4.6s）。
- **风险**：
  - SSE 事件顺序是 PRD §5.4 的硬契约：`turn_start → retrieval → modality_decision → token* →
    artifact → citations → turn_end` **顺序不可变**。并行后产物可能先于正文完成，必须**先缓冲
    artifact 结果，等所有 token 发完再发**。缓冲期间若正文抛错降级 mock，错误归因会变复杂。
  - 两个并发 LLM 请求对 rate limit 的影响未测。
- **对契约的影响**：**中等**（事件顺序必须保持，实现上要加一层缓冲；不需要改字段）。

### 手段 4：产物生成改流式 + 增量解析

- **预期收益**：非流式调用必须等整份 JSON 才返回第一个字节。改 `stream=True` 后首字在
  **45,830ms**（5 页样本）就到，而不是 57,435ms → **省 11.6 秒（20%）**；
  若按 slide 粒度增量解析，第一页可渲染时间约 `10.8 + 48 = 估算 59s`，省 7 秒左右。
- **风险**：JSON 增量解析要处理未闭合的数组/对象；`parse_artifact_spec` 只能在完整后才校验，
  渲染了错误内容再回滚会造成「界面闪变」；实现复杂度明显高于手段 1。
- **对契约的影响**：**低**（最终 spec 不变）。

### 手段 5：给 `complete_json` 加 `max_tokens`

- **预期收益上限 11.6 秒**（内容生成阶段全部时长，5 页样本），实际可能只有 2~4 秒。
  而且 `max_tokens` 是否也约束推理 token **未验证** —— 如果推理不受约束，收益接近 0。
- **风险：高**。截断 → JSON 不合法 → `contract_retry` 触发，**一次重试就是一次完整调用**。
  按当前 v4-pro 中位 55.5 秒算，最坏情况 `55.5 × 3 = 166.5 秒`，比不优化糟 2.5 倍。
  这恰好是 IMPL-NOTES E11 问题 1 踩过的坑（重试三次、错误数越改越多、最后降级 mock）。
- **对契约的影响**：**高**（截断即失败）。
- **建议**：只在配合手段 2「分批下发」把每批输出压到很小（如 2 页 ≈ 3,300 token）之后再考虑。

### 手段 6：缩短 `_ARTIFACT_CONTRACT` / 提示词 —— ❌ **建议直接否掉**

- **预期收益 ≈ 0**。实测证据：响应头 TTFB 243~535ms、`prompt_tokens` 仅 1,005；
  真正慢的是推理阶段（36~54 秒）。即使把 1,395 字符的契约砍掉一半，也只影响预填充，
  省不到 0.5 秒。
- **风险**：契约变短 → 模型自创字段 → 校验失败 → 重试 → **更慢**。IMPL-NOTES E11 已经
  完整记录过这条路径（错误数 15 → 21 → 26，三次调用后降级 mock）。
- 这是本次测量**最有价值的否定结论之一**：它把一个「看起来最直观」的优化方向用数据排除了。

### 手段 7：`effort=max` / 更高质量档 —— ❌ 反向，不建议

方向上必然更慢（`low` 都已经更慢），且会消耗更多 token。未测，不建议投入。

### 汇总对比

| 排序 | 手段 | 预期收益（实测推导） | 整轮耗时 | 风险 | 对契约影响 |
|---|---|---|---|---|---|
| 1 | 产物换 flash | 55.5s → 10.1s | 66.3s → **约 20.9s**（−68%） | 中（形态覆盖未测、retry 率未测） | 零 |
| 2 | 分批下发（并行） | 首屏 −19s，总 −15s | 首屏 **约 47.3s**，总 约 51s | 高（跨批约束、版本语义） | 中（加事件） |
| 3 | 正文/产物并行 | −10.8s | 66.3s → 约 55.5s | 中（事件顺序缓冲） | 中（不改字段） |
| 4 | 产物改流式 | −11.6s | 首屏 约 59s | 中高（增量 JSON 解析） | 低 |
| 5 | 加 `max_tokens` | ≤ 11.6s，实际 2~4s | — | **高**（截断→3 倍耗时） | 高 |
| 6 | 缩短提示词 | ≈ 0 | — | 中（重试风险） | 中 |
| 7 | 提高 effort | 负数 | — | — | — |

**推荐组合**：手段 1（先补 3 种形态 + retry 率验证）为主，叠加手段 3（并行，省 10 秒且与手段 1 正交）。
手段 2 留给「首屏可见时间」成为下一轮瓶颈时再做 —— 在手段 1 落地后，画布 21 秒出全量产物，

## 六、与 `P1-03-latency-PRD.md` 的 T1–T5 对照（回填 PRD §2.1 与 Q9）

PRD 的 Q9 要求本次剖析补齐 T2 / T3 / T5 的当前值以及 70 秒的测量条件。逐条回填：

| 编号 | 指标 | PRD 里的当前值 | **本次实测** | 判定 |
|---|---|---|---|---|
| **T1** | 正文首 token（TTFT） | 2.9 s | **4.616 s**（P50，n=3；min 3.750 / max 5.202） | ❌ **超 3.0s 目标**，见 6.1 |
| **T2** | 画布首次反馈（骨架屏） | 待确认 | **未测**（纯前端本地状态，本次剖析不覆盖前端） | — |
| **T3** | 第一份可交互产物 | 待确认 | **≈ 66.3 s**（当前只有一次 `artifact` 事件，且它在完整产物之后才发；分批改造前 T3 恒等于 T4） | ❌ 远超 20s 红线 |
| **T4** | 完整产物就绪 | ≈ 70 s | **66.285 s**（P50，n=3；min 53.514 / max 77.642） | 落在红线内、未达 45s 目标 |
| **T5** | 增量 patch 回合 | 待确认 | **26.825 s**（n=1），= create 的 **40.5%** | ✅ 满足 P0-10③ ≤ 50% |

**T3 的解读要点**：现在没有分批，`artifact` 事件只有一次、且携带完整 spec，所以「第一份可交互产物」
和「完整产物」是同一个时间点。**T3 = T4 = 66.3 秒**。这正是 PRD 说「真正要优化的是第二层」的
数据依据 —— 改造前 T3 没有任何独立优化空间。

**70 秒的测量条件（PRD 要求的归因）**：
`deepseek-v4-pro` 生成 5~8 页 PPT 契约、`contract_retry = 0`、含落库、本机直连 DeepSeek、
样本教材 113 页 / 65 切片。本次 3 次实测 53.5 / 66.3 / 77.6 秒，中位 **66.3 秒**，
与 HANDOVER 记录的「约 70 秒」一致；`max = 77.6s > 目标 45s × 1.5`，方差主要来自模型推理长度
（`completion_tokens` 3,676~5,736，跨度 56%）。

**对 PRD 目标可行性的判断（只给数据，不做决策）**：
- **T4 ≤ 45 s**：靠分批下发**做不到**（分批只改变可见时机，不减少生成量，串行分批反而更慢）。
  只有「换 generator 档位」（实测 55.5s → 10.1s）或「正文/产物并行」（省 10.8s）能压下来。
  单靠并行是 55.5s，仍不达 45s；**必须叠加换档位才可能达标**。
- **T3 ≤ 15 s**：即使采用「首批 2 页 + 分批」，按实测 2 页 = 36.5 秒，T3 ≈ 10.8 + 36.5 = **47.3 秒**，
  **远超 20 秒红线**。若 generator 换成 flash（实测整份 5~6 页 10.1 秒），T3 可以做到
  **约 11~21 秒**，才谈得上 15 秒目标。
- **结论**：PRD 里「三条压缩路径都需要实测」（§2.2）—— 本次实测结果是：
  **「批次间流水线化」收益 10.8s、「单批输出规模控制」收益次线性（5→2 页只省 36%）、
  「generator 档位」收益 45.4s（最大且最确定）**。

## 七、顺带发现的两个问题（不属本次任务，供 PM / 架构师判断）

### 7.1 TTFT 中位数 4,616ms，已超出 P0-05① 的 3,000ms 预算

3 次实测：**3,750 / 4,616 / 5,202ms**，中位 **4,616ms**。HANDOVER 与 IMPL-NOTES E11 记录的
「2.9 秒 / 3.2 秒」是在旧机器 + 旧网络下测的，本机复现不到。

这不是本次改动引起的（业务代码零改动），但**意味着 P0-05① 在本机已经不达标**。
需要 PM 明确：这个预算是按哪台机器/哪条网络定的？如果按本机复测，标准是否要重标？

### 7.2 `source_ref` 有时不带页码

契约要求 `source_ref` 格式为 `"4.1.3, p.76"`，但 3 次基线产物中**有 1 次**全部写成 `"4.1.2"`
（缺 `p.N`）。schema 只校验「是字符串」，所以不会被拒绝，也不会触发重试。
后果是「每条事实带页码引用」这个 P0 核心卖点在那一份产物上无法回溯到具体页。
`_source_ref_pages()`（本脚本新增）已经把这类情况量化出来，可作为后续验收指标。

## 九、如何重跑

```bash
cd <项目根>

# 完整剖析：3 次基线 + 页数对照 + effort 对照（约 6 分钟，消耗 token）
backend/.venv/Scripts/python.exe scripts/profile_latency.py

# 只要基线分段表（不跑对照实验，最省 token）
backend/.venv/Scripts/python.exe scripts/profile_latency.py --runs 3 --no-probes

# 只重跑模型对照（复用上次缓存的提示词，不重复跑基线）
# 注意：与 LLM_MODEL_GENERATOR 同名的模型会被自动跳过，所以这里只列 flash
backend/.venv/Scripts/python.exe scripts/profile_latency.py \
    --runs 0 --probe-pages "" --probe-efforts "" \
    --probe-models deepseek-flash

# 只重跑页数对照
backend/.venv/Scripts/python.exe scripts/profile_latency.py --runs 0 --probe-pages 5,2 --probe-efforts ""

# 只测 patch 回合（复用库里已有产物，不重跑全量生成）
backend/.venv/Scripts/python.exe scripts/profile_latency.py \
    --runs 0 --reuse-corpus --patch-turns 1 --no-probes
```

参数说明见 `--help`。要点：

- `--runs 0` 表示跳过基线回合、只用 `--prompt-cache` 里缓存的提示词跑对照实验（**不消耗基线 token**）
- `--reuse-corpus` 复用剖析库里已解析好的工作区，跳过重新入库；会优先挑「已经有产物」的那个，
  这样 `--patch-turns` 才有基线可点
- 剖析数据全部落在 `backend/data/profile/`（已在 `.gitignore` 中忽略），与正式 `data/app.db` 隔离，跑完可整目录删除
- 探针产物的原始 JSON 落盘在 `backend/data/profile/probe-outputs/`，可直接人工核对内容质量
- 脚本会**自动把超时放宽到 300 秒**（否则「慢」会被掩盖成「超时重试」），生产配置不受影响
- 脚本对 `backend/app/` **零改动**，全部埋点靠运行期 monkeypatch，进程退出即失效
