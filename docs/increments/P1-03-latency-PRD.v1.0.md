## 0. 本次变更摘要

### 0.1 一句话

> **把「等 70 秒」变成「先给两页能翻的，剩下的边看边长」。**

### 0.2 为什么要做

真实模式下学生提问后：左侧文字 2.9 秒开始流（已达标），但**右侧画布空白约 70 秒**。学生在这个窗口里只有一段静态文字，无法翻页、无法点元素、无法验证「系统真的在为我做课件」。这是当前体验唯一的断点，也是 `HANDOVER.md` 诚实清单里的第一条已知限制。

### 0.3 本次新增什么

| 新增 | 不新增 |
|---|---|
| 按「学生先看到什么、后看到什么」分层的 5 个时间指标（T1–T5） | 不新增任何产物形态、布局、交互能力 |
| 分批下发 + 渐进渲染的 6 条需求（P1-03-01 ~ 06） | 不修改任何 P0 需求的行为定义 |
| 分批场景下的失败降级矩阵（F1–F5）与事故红线（R1–R6） | 不新增用户可见的产品入口 |
| 可脚本化测量的验收方案（5 个时间戳 + 采样口径） | 不做前端渲染性能优化、不做缓存预生成 |

### 0.4 与 P0 的关系（不可让渡）

| P0 条目 | 本次的态度 |
|---|---|
| P0-05① TTFT ≤ 3 秒 | **继续有效，且不得回退**。本次所有优化都不得以牺牲 TTFT 换取（例如「等 AST 一起发」） |
| P0-05④ 禁止编造页码 / 课本未覆盖必须提示 | **继续有效**。不得为提速放宽 `GRADER_CONTENT_HIT_MIN_RATIO`，不得跳过引用合法性后校验 |
| P0-07② 单次生成 ≥ 5 页、Pydantic 校验通过 | **继续有效**。分批是「先发一部分」，不是「少发一部分」 |

## 1. 问题定义

### 1.1 手上可信的数字（只有这些）

| 数字 | 含义 | 来源 | 可信度 |
|---|---|---|---|
| **2.9 s** | 真实 DeepSeek 链路 TTFT（首 token） | `HANDOVER.md` 一、IMPL-NOTES §六 | 实测 |
| **≈ 70 s** | 真实模式生成 5 页 PPT 的整份耗时 | `HANDOVER.md` 一 / 六-1 / 附·已知限制；`agent_engine.py` `_generate_spec_stream` 注释 | 记录值 |
| **0.41 s** | 113 页 PDF 解析耗时 | IMPL-NOTES §六 | 实测（本次不涉及） |
| 其余任何「当前实际耗时」 | — | — | **`待基线剖析确认`**（工程师并行执行任务 #2） |

> **诚实声明**：70 s 这个数字**没有标定测量条件** —— 未记录模型档位、页数、是否含 `contract_retry`、是否含落库、是否含正文流耗时。
> 因此本文所有「当前值」一律写 `待基线剖析确认`，不臆测拆分比例。基线剖析的产出必须先填回 §2.1 的空格，目标值才算冻结。

### 1.2 为什么「总耗时 70 秒」不是一个可用指标

因为它把三件对体验影响完全不同的事揉成了一个数：

| 学生此刻在做什么 | 决定体验的是什么 | 70s 能不能回答 |
|---|---|---|
| 按下回车，怀疑系统卡死 | 第一个字什么时候出现 | 不能（2.9s 已达标的正是这一层） |
| 读完讲解文字，想看课件 | 画布上第一份能翻、能点的东西什么时候出现 | **不能** |
| 已经在看第 2 页，想知道第 5 页什么时候好 | 全部就绪要多久 | 能，但这一层是最不痛的 |

**结论：真正要优化的是第二层，不是总和。** 一个「首屏 8 秒出 2 页、45 秒补齐 5 页」的实现，体验显著优于「12 秒一次性出 5 页」，即使后者总耗时更短。

### 1.3 学生在这一分钟里的注意力分布（目标取值的依据）

1. **0 – 3 s**：只关心「有没有反应」。超过 3 s 开始怀疑网络（Nielsen 的 1 秒「思路不断」/ 10 秒「注意力上限」阈值是通用 UX 经验值，非本项目实测）。
2. **3 – 20 s**：在读左侧流式正文。正文约 150–200 字（4 条事实 + 建议形态），按常见中文阅读速度 300–500 字/分钟（通用经验值）约需 20–40 秒读完并理解。
   → **画布若能在正文读完之前出现，学生的注意力不会发生「等待 → 切换任务」的断裂。这是 T3 取 15 秒的核心依据。**
3. **20 – 70 s**：注意力无处安放。若此时画布仍空，学生会去点目录树、切标签页、或直接重新提问（产生并发请求与浪费的 token）。
4. **补充判断**：学习场景比娱乐场景**更能容忍总时长**（学生本来就要读、要想），但**更不容忍「不知道还要多久」**。所以「分批 + 真实进度」的价值高于「绝对速度」。

## 2. 分级时间目标（本次 PRD 的核心）

### 2.1 目标表

> **三层结构 + 两个守卫指标。** 每条都有：测量点（怎么测）、红线（超即失败）、目标（应达到）、期望（有余力则达）。

| 编号 | 指标 | 测量点（详见 §7） | 红线 | **目标** | 期望 | 当前值 |
|---|---|---|---|---|---|---|
| **T1** | 正文首 token 时间（TTFT） | 收到第一个 `token` 事件 | ≤ 3.0 s | **≤ 3.0 s（不得回退）** | ≤ 2.5 s | **2.9 s**（实测） |
| **T2** | 画布首次反馈（骨架屏/占位） | 前端本地状态切换 | — | **≤ 0.5 s** | ≤ 0.2 s | `待基线剖析确认`（可能已达标） |
| **T3** | 第一份**可交互**产物出现 | 收到首个可渲染 `artifact` 事件（页数 ≥ 1） | ≤ 20 s | **≤ 15 s** | ≤ 10 s | `待基线剖析确认` |
| **T4** | 完整产物全部就绪（含落库） | 收到 `turn_end` | ≤ 70 s（不得劣于记录基线） | **≤ 45 s** | ≤ 30 s | **≈ 70 s**（记录值） |
| **T5** | 增量 patch 回合耗时 | 收到 `turn_end`（patch 回合） | 不得劣于本次改动前 | **≤ 同规模全量生成的 50%**（沿用 P0-10③） | 同左 | `待基线剖析确认` |

**T3 的适用范围**：本次只对 **PPT** 生效。2D / 3D 是否纳入 T3 → 见 Q6。

### 2.2 每条目标的取值依据

**T1 ≤ 3.0 s（不得回退）**
已有验收标准 P0-05① 就是 3 秒，实测 2.9 秒。本次不提高要求，只设**回退禁令**：任何为了「让画布早点有东西」而把 AST 生成前置到正文之前的做法，都会把 T1 从 2.9 s 推向 30 s 以上（IMPL-NOTES E11 记录过误用重模型导致 TTFT 55 s 的教训）。**T1 是本次改动的护栏，不是本次的目标。**

**T2 ≤ 0.5 s**
纯前端本地状态，不依赖后端任何事件。依据：1 秒内无反馈即打断思路（通用 UX 阈值）。这一层几乎零成本，但要**显式保护** —— 分批改造最容易的失误就是「等后端第一个批次事件到了才画骨架屏」，把 T2 从 0 秒拖到十几秒。

**T3 ≤ 15 s（目标）/ ≤ 20 s（红线）/ ≤ 10 s（期望）**
- 主依据：§1.3 第 2 条 —— 15 s 落在「学生读完正文之前」，注意力不断裂。
- 次依据：15 s ≈ 5 × T1 量级，学生感知为「同一个过程的延续」，而不是「另一个任务」。
- 红线取 20 s：超过 20 s，学生读完正文后仍面对空画布，分批的收益基本归零，改造不值得做。
- 期望取 10 s：留一档余量给「首批 1 页 vs 2 页」「是否引入流式 JSON 解析」这些待定机制（Q2、Q7）。**15 s 是按「首批 2 页」估算的产品判断，能否达到取决于实测（`待基线剖析确认`）。**

**T4 ≤ 45 s（目标）/ ≤ 70 s（红线）**
- 70 s 是现有记录值，作为**不得劣于**的底线（分批不得让总时长变长）。
- 45 s 是目标：降约 35%。**这个目标能否达成，取决于总耗时能否被并行化压缩，而不只是被切分** —— 分批本身只改变「何时可见」，不减少生成量。三条可能的压缩路径（批次间流水线化、单批输出规模控制、generator 档位）都需要实测，见 Q1、Q5。
- 不设更激进的目标：T4 已超过 10 秒注意力阈值，继续压它的边际体验收益远低于压 T3。

**T5 不得劣于改动前**
patch 是「点一处改一处」的招牌能力（P0-10），它的耗时体验必须独立于本次改动。分批在 patch 场景无收益（patch 本来就是单节点子树），却会引入 base_version 复杂度 → **patch 明确不走分批**。

### 2.3 判定口径（防止数字被玩坏）

| 规则 | 说明 |
|---|---|
| 统计量 | 真实链路采样 **≥ 5 次，取中位数（P50）** 判定；同时记录 min / max。max 不作门禁，但 > 目标 × 2 时必须在报告里归因 |
| **mock 数字不得用于判定 T1/T3/T4** | mock 是毫秒级，用它充抵真实目标等于自欺（IMPL-NOTES E11 教训 2：mock 全绿 ≠ 功能可用） |
| 冷启动隔离 | 进程冷启动后的第一次请求（含连接池建立）单独记录，**不参与判定**，但必须记录 |
| 环境固定 | 同一模型档位、同一份 PDF、同一组 3 条固定 PPT 问句；环境变更后需重跑基线 |
| 达标定义 | T1、T3、T4 三条**全部**达到「目标」列，才算本次需求通过。任一落在「红线」以外 → 不通过 |

## 3. 增量需求池

> **全局前置条件**：本次所有改动完成后，后端 244 测试、前端 153 测试、端到端冒烟 38 项必须仍全绿；任何一条转红即视为本次改动破坏了 P0 基线，不得合并。

### P1-03-01 分批下发（仅 PPT）

**做什么**：PPT 产物按批下发。首批必须携带可直接渲染的完整页（≥ 1 页），后续批次增量追加，最终合并为完整 spec。

| # | 验收标准（可脚本化） |
|---|---|
| ① | 一次 `create_artifact` 回合中，PPT 产物下发 **≥ 2 个** `artifact` 事件（首批 + ≥ 1 次追加），且首批 `spec.slides.length` < 最终页数 |
| ② | 首批 spec **单独**通过 `parse_artifact_spec()` 校验。**不得为了放行而修改 `SlideDeckSpec` / `SlideNode` 的任何既有约束**（`slides` 已是 `min_length=1`，1–2 页的部分 spec 天然合法，无需放宽任何契约） |
| ③ | 最终合并 spec 与「关闭分批」路径对同一 query 的结果比对：页数均 ≥ 5（P0-07②）、布局种类均 ≥ 3、`node_id` 全局唯一无重复、每页 `source_ref` 页码均落在该回合检索命中的页码集合内（P0-05④ 不因分批放松） |
| ④ | 追加批次**不得改动已下发页的任何字段**（用 `canonical_json` 字节比对，沿用 IMPL-NOTES E8 的序列化口径） |
| ⑤ | 批次总数、已下发页数、预期总页数可从 `turn_end` 事件读出（字段形态由架构师定） |
| ⑥ | **mock 模式走同一条分批路径**，且同一输入两次生成的分批结果完全一致（沿用 P0-12② 的确定性要求） |
| ⑦ | 分批路径下的 `artifact` 事件在 SSE 中的相对顺序必须稳定：首批（create）→ 追加（append/patch）→ `citations` → `turn_end` |

### P1-03-02 渐进渲染不打断阅读

**做什么**：首批到达即可翻页、可点元素；后续批次到达时把新页「贴上去」，不打断学生当前所在页。

| # | 验收标准 |
|---|---|
| ① | 首批到达 → 画布从骨架屏切到可交互态 ≤ **100 ms**（前端本地测量） |
| ② | 追加批次到达时，画布 `currentSlideIndex` **保持不变**（学生看第 2 页，追加第 3–5 页后仍在第 2 页） |
| ③ | 追加只新增节点，已渲染页不重新挂载（用渲染计数 / `React.memo` 断言，不得出现整树重渲染） |
| ④ | 生成中点已到页 → 锚点 chip 正常出现（「可交互」的判定标准就是这条能过） |
| ⑤ | **生成中禁止发起锚点追问**：锚点 chip 可显示但发送按钮禁用，提示「正在生成，稍候可追问」。理由：patch 需要稳定的 `base_version`，打到中间态必然产生 `PATCH_BASE_VERSION_CONFLICT`（IMPL-NOTES E9-2 已记录过这类 409） |
| ⑥ | 缩略图条在生成中显示**全部预期页**的格子：已到页实心，未到页虚线占位（见 §6） |

### P1-03-03 批次进度可见（且必须真实）

| # | 验收标准 |
|---|---|
| ① | 生成中画布常驻「已生成 X / Y 页」真实计数，X 随批次递增，Y 为预期总页数 |
| ② | 全部就绪时进度标识消失，不残留 |
| ③ | **禁止定时器模拟进度**：注入 3 s 延迟后，进度值不得自行前进。进度只能由真实批次事件驱动（这是 P0-12③「不可静默伪装」的同一条原则） |

### P1-03-04 中途失败的可见与可续（详见 §5）

| # | 验收标准 |
|---|---|
| ① | 模拟第 k 批失败（1 < k ≤ n）：画布保留已到的 (k−1) 批，显示「已生成 X / Y 页，生成中断」，并提供「继续生成」与「重新生成」两个动作 |
| ② | 失败后**刷新页面，已到部分仍在**（已下发部分必须落库，见 §5.2） |
| ③ | 失败后画布不得空白，也不得把不完整产物显示为「已完成」（见 R1） |
| ④ | 首批即失败：沿用现有降级链（3 次校验重试 → mock 降级），行为与改动前一致，不新增分支 |

### P1-03-05 回退开关（可退回一次性下发）

| # | 验收标准 |
|---|---|
| ① | 提供配置项（如 `ARTIFACT_BATCHING_ENABLED`）关闭分批；关闭后 SSE 事件序列与改动前**完全一致**（事件名、顺序、数量逐一比对） |
| ② | 关闭状态下 T1 / T4 / T5 均不劣于改动前（`待基线剖析确认` 提供对比基线） |
| ③ | 开关默认值由架构师定（建议默认开启，见 Q8），但**必须存在且可被环境变量覆盖** |
| ④ | 开关关闭时前端不得残留进度 UI、不得残留占位格 |

### P1-03-06 耗时埋点与测量脚本

| # | 验收标准 |
|---|---|
| ① | 提供一键脚本，对固定 3 条 PPT 问句各采样 ≥ 5 次，输出 T1 / T2 / T3 / T4 / T5 的 min / P50 / max 表格（Markdown）+ 原始 JSON |
| ② | 脚本必须**同时**记录 `turn_end.duration_ms`（服务端自报）与客户端计时，两者偏差 > 5% 时打印告警（防止「服务端算得好看、用户实际在等」） |
| ③ | 脚本额外验证「刷新可见性」：`turn_end` 之后 `GET /api/artifacts/{id}` 返回的页数 == 画布页数 |
| ④ | 脚本默认只在手动触发时运行，**不进入 CI 门禁**（真实链路消耗 token）；mock 模式的耗时检查可以进 CI |
| ⑤ | 产出落到 `docs/increments/P1-03-baseline.md`（基线）与 `P1-03-after.md`（优化后），供评审对照 |

## 4. 范围边界（明确不做）

### 4.1 内容质量红线（不得为提速让渡）

| 不做 | 原因 |
|---|---|
| 不减少 PPT 最少页数（P0-07② ≥ 5 页） | 「先出 2 页」是分批，不是缩水。最终产物必须仍是完整课件 |
| 不放宽 `GRADER_CONTENT_HIT_MIN_RATIO`（0.45）或任何检索阈值 | 该阈值是 18 条无关问题 / 16 条相关问题实测标定的（IMPL-NOTES E7），换阈值等于把「课本未覆盖」判定改成掷骰子 |
| 不跳过正文页码合法性后校验（`_drop_invalid_citations`） | 分批改造最容易顺手「为了省一次遍历」删掉它，等于拆掉 P0-05④ 的最后一道闸门 |
| 不降低布局多样性（≥ 3 种）与 `source_ref` 真实性 | 快不能靠让模型瞎编 |
| 不用 mock 产物冒充真实产物、不用 mock 耗时冒充真实耗时 | P0-12③ 的同一条原则 |

### 4.2 本次不改的系统部件

| 不做 | 原因 |
|---|---|
| 不改检索算法（BM25 权重 / 向量 / 实词命中率 / Top-K） | 与耗时无关，改动风险高于收益 |
| 不换数据库、不做表结构大改 | 若分批必须新增字段，只允许「新增可选列」这一种形态，且需架构师明确批准（→ Q3） |
| 不改分层路由的模型分配（`LLM_MODEL_ROUTER` / `LLM_MODEL_GENERATOR`） | E11 已裁定：正文用轻量档保 TTFT，spec 用重档保准确率。**换 generator 档位属独立变更，需单独评估质量影响**，不在本次 |
| 不做 2D / 3D 的分批 | 关键帧 / 节点树的分批语义与 PPT 页列表不同，复杂度不对等；本次痛点集中在 5 页 PPT 场景（→ Q6） |
| 不做 patch 路径的分批 | patch 天然是小范围单节点，分批无收益却引入 base_version 复杂度（见 T5） |
| 不做前端渲染性能优化 | 3D 首帧 ≤ 5 s（P0-09③）是独立指标，与本次无关 |
| 不做缓存 / 预生成（同章节第二次提问复用产物） | 属 P2，且涉及「产物过期如何判定」，本次不碰 |
| 不做登录、多用户、并发配额 | 与本次无关 |
| 不修改 `docs/PRD.md` 的任何既有条目 | 增量文档只新增，不回改上游 |

### 4.3 明确不承诺

- 不承诺 T4 降到 45 s 以下；不承诺「实时逐页渲染」（那需要流式 JSON 解析，见 Q7）。
- 不承诺分批在弱网 / 代理缓冲场景下的表现（SSE 经 nginx 缓冲会把分批压成一次性，属部署问题，见 §5.5）。

## 5. 失败降级要求

> 分批的本质风险：**画布上出现了「半份」，而系统以为「整份」**。本节就是为了让这句话不可能成立。

### 5.1 失败场景矩阵

| 编号 | 场景 | 触发条件 | 用户看到 | 数据落库 | 可续 / 可退 |
|---|---|---|---|---|---|
| **F1** | 首批即失败 | LLM 超时 / 首批 3 次校验不过 | 骨架屏 → 沿用现有降级链：`error`（retryable）+ 3 次重试提示 → mock 降级产物。**行为与改动前一致** | 无产物；或 mock 产物 version=1 | 沿用现有（无需新增） |
| **F2** | 中间批次失败 | 第 k 批失败（1 < k ≤ n） | 保留已到 (k−1) 批，画布标注「已生成 X / Y 页，生成中断」，出现 [继续生成] [重新生成] | **已到部分必须落库**（见 §5.2），并标记为不完整 | 续：只补剩余批次（需 Q5 确认能力）；退：整份重生成 → version+1 |
| **F3** | 流被中断 | 关页面 / 断网 / 代理超时 | 重进会话：看到已落库部分 + 「上次生成中断」提示 | 已到部分落库（服务端不因客户端断开而丢数据） | 同上（需 Q4 确认服务端断连后的行为） |
| **F4** | 用户主动停止 | 点「停止生成」 | 保留已到部分 + 明确「已停止（X / Y 页）」 | 已到部分落库 | 可续 / 可退，同 F2 |
| **F5** | 某批次校验失败（非首批） | 该批 AST 非法 | 该批重试 ≤ 3 次（沿用现有策略）；仍失败则**跳过该批**并在画布标「第 X 页生成失败」，不阻塞其余批次 | 已到部分落库 | 可续：仅重试失败批 |

**统一原则**：
1. **已下发的必须可恢复**（R2）。宁可多落一次库，也不能让刷新变成「什么都没了」。
2. **不完整必须被标记**（R1）。任何 UI 状态都不得让半份产物看起来像完成品。
3. **失败不扩大**：一批失败不牵连已成功的批次，也不让正文（已流给用户的讲解）消失。

### 5.2 落库状态要求

| 要求 | 说明 |
|---|---|
| 已下发批次必须持久化 | 每批到达即写库（或至少在 `turn_end` / 断连 / 停止时写入已到部分）。这是 R2 的唯一保障 |
| 中间态**不得**改写历史版本 | 允许覆盖「当前 artifact 行」，**禁止**改写 `artifact_versions` 里已有的任何一行（P0-11③）。具体实现方式（同版本覆盖写 / 中间批次不建版本 / 新增状态列）→ Q3 |
| 完成态与中间态必须可区分 | 刷新后前端必须能判断「这是完整产物还是半份」。承载位置（spec 可选字段 / API 响应旁路字段 / 独立状态列）→ Q3，但**不能没有** |
| 不完整产物的 patch 权限 | 不完整产物**不允许**发起锚点追问（前端禁用），避免在中间态上叠 patch 产生 base_version 混乱 |
| `turn_end` 必须必发 | 无论成败，`turn_end` 都要发出（§5.4 规则②已如此要求），且携带完成度信息（P1-03-01⑤） |

### 5.3 事故红线（出现任意一条即判本次需求失败）

| 编号 | 禁止出现的事故形态 |
|---|---|
| **R1** | 画布显示半份产物，但 UI 上没有任何「未完成」标记（把不完整当完整） |
| **R2** | 已下发的批次刷新后消失（画布有、库里没有） |
| **R3** | 分批导致页序错乱 / 重复页 / `node_id` 冲突 / 缺页，且最终合并结果与一次性生成不一致（P1-03-01③ 反例） |
| **R4** | 为凑首批而降低质量：编造页码、放宽 grader 阈值、最终页数 < 5、布局只剩 1 种 |
| **R5** | 生成中允许 patch，产生 `PATCH_BASE_VERSION_CONFLICT` 或把 patch 结果写到中间版本上 |
| **R6** | 用定时器/假进度条伪造批次进度；或用 mock 耗时数据宣称 T3/T4 达标 |

### 5.4 回退开关（必须可一键退回老路径）

- 关闭分批后，系统行为必须与本次改动**逐字节等价**（P1-03-05①）。
- 回退不依赖代码回滚，只依赖配置。理由：真实链路出问题时，产品侧需要「一个环境变量把体验切回已知可用状态」，而不是等一次发布。
- 回退开关不改变产物内容，只改变下发节奏。

### 5.5 部署侧注意（写进运维检查项）

SSE 经反向代理时，若代理开启响应缓冲（nginx 默认 `proxy_buffering on`），后端的分批会被压成一整块，**T3 直接退回 T4**。要求：部署文档与启动脚本必须确认 SSE 端点关闭缓冲（`X-Accel-Buffering: no` 或等价配置），并在冒烟脚本里加一条「分批事件到达时间不集中」的检查。

## 7. 验收测量方案（可脚本化）

### 7.1 五个时间戳定义（客户端单调时钟，t0 为基准）

| 时间戳 | 定义 |
|---|---|
| `t0` | 客户端发出 `POST /api/chat/stream` 的瞬间（`performance.now()`） |
| `t_turn_start` | 收到 `turn_start` 事件 |
| `t_retrieval` | 收到 `retrieval` 事件（含 `grader_status`） |
| `t_first_token` | 收到**第一个** `token` 事件 → **T1 = t_first_token − t0** |
| `t_first_artifact` | 收到**第一个**携带可渲染内容的 `artifact` 事件（`spec.slides.length ≥ 1`，含「部分」标记的批次）→ **T3 = t_first_artifact − t0** |
| `t_turn_end` | 收到 `turn_end` → **T4 = t_turn_end − t0** |
| `t_persist_ok` | `turn_end` 之后 `GET /api/artifacts/{id}` 返回成功且页数一致 → 验证「刷新可见」（P1-03-06③） |

- **T2** 由前端本地测量（骨架屏挂载时间戳 − 提交动作时间戳），不依赖后端事件。
- **T5** 用同一脚本跑一条 patch 问句，取 `turn_end.duration_ms`，与同规模 create 回合对比。
- 每个时间戳同时记录服务端自报值（`turn_end.duration_ms` / `ttft_ms`）用于交叉校验。

### 7.2 采样与判定

1. 固定 3 条 PPT 问句（覆盖 title_hero / bullet_points / comparison 三类布局），每条采样 ≥ 5 次。
2. 取 P50 判定；记录 min / max；`max > 目标 × 2` 需归因。
3. 冷启动第一次请求单独记录、不参与判定。
4. mock 模式单独跑一遍（验证分批路径本身正确），**数字不用于 T1/T3/T4 判定**。
5. 输出：`docs/increments/P1-03-baseline.md`（改动前）与 `P1-03-after.md`（改动后）并排对照表。

### 7.3 判定表（评审用）

| 指标 | 改动前（P50） | 改动后（P50） | 目标 | 结论 |
|---|---|---|---|---|
| T1 TTFT | 2.9 s | 待填 | ≤ 3.0 s | 待填 |
| T2 画布首反馈 | 待基线剖析确认 | 待填 | ≤ 0.5 s | 待填 |
| T3 首批可交互 | 待基线剖析确认 | 待填 | ≤ 15 s | 待填 |
| T4 完整就绪 | ≈ 70 s | 待填 | ≤ 45 s | 待填 |
| T5 patch | 待基线剖析确认 | 待填 | ≤ 全量 50% | 待填 |

> 本表由任务 #5（全量回归 + 耗时指标验证）填完。**表格未填满 = 本次需求未完成。**
