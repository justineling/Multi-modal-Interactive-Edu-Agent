## 一、结论行

**唯一需要决策的点（G3）**：`_artifact_prompt` 从头到尾没有把页码告诉模型，

- **v4-pro**：写 `4.3.1, p.?` —— 页码**可见地缺失**

| 选项 | 动作 | 成本 | 后果 |

**三层指标的口径**（任务书要求，不许合并成一个「成功率」）：

1. **单次调用合法率** = 未触发校验错误的调用数 / 真实 HTTP 调用总数
2. **回合最终通过率** = 最终 spec 来自 LLM（≤3 次重试内成功）的回合 / 总回合
3. **降级 mock 率** = 三次都失败、退回演示生成器的回合 / 总回合

口径自校验：`合法调用 + 失败调用 == 真实调用总数`，三个形态全部 ✓。

### 统计效力：11 回合**能否决，不能证实**（不要读成「retry 率 ≤ 10%」）

按 rule of three，`n` 次全过时真实失败率的 95% 置信上界是 `3/n`：

| 样本 | 观测 | 95% 置信上界 | 能下的结论 |
|---|---|---|---|
| n = 3 | 0 次重试 | **≈ 63%** | 等于没估（任务 #2 的 3 次样本就属于这一档） |
| **n = 11（本次）** | **0 次重试** | **≈ 27%** | **证不了 ≤10%；只能记「未能否决」** |
| n = 30（阶段二） | 0 次重试 | ≈ 10% | 这才叫统计证实 |

反方向是不对称的：**11 回合里只要出现 2 次重试（18%）就足以证明「明显超 10% 线」并直接否决**。
所以本轮的定位是**否决门**，不是证实。

> **口径纪律（按 PRD §4.3 阶段一 + 产品经理的更正）**：
> 正确写法是「阶段一 0/11，未达统计证实，待阶段二」；
> **不得写成「11 回合全过，所以 retry 率 ≤ 10%」** —— 那是把「未能否决」当成「已经证实」，统计误用。

## 五、关键发现：`source_ref` 的页码可回溯性目前是假的（模型无关）

### 5.1 证据

`_artifact_prompt` 实际发出去的提示词只有三段：

```
目标形态：ppt
章节：4.3.1 Pilihan Raya 1955
用户诉求：4.3.1 1955 年选举为什么重要，讲清因果
课本事实（只能依据以下内容生成，不得编造页码或事实）：
- （8 条句子，纯文本，**不含任何页码**）
【输出契约：ppt】… 最小合法示例 … "source_ref":"4.1.1, p.76" …
```

`MockContext.pages` 里其实**有**页码（来自检索切片的 `page_start`），但它**没有进提示词**。
模型能看到的唯一页码，是契约示例里那个硬编码的 `p.76`。

于是三种失败形态：

| 模型 | 小节 | 真实允许页 | 模型写的 `source_ref` | 性质 |
|---|---|---|---|---|
| flash | 4.1.2 | 72~89 | `4.1.2, p.76` | **偶然正确**（真实页恰好是 76） |
| flash | 4.2.1 | 70~91（含 76） | `4.2.1, p.76` | 偶然正确 |
| flash | 4.3.1 | 71~91（**不含 76**） | `4.3.1, p.76` | **静默编造** |
| flash | 5.1.1 | 92~109 | `5.1.1`（无页码） | 不可回溯 |
| flash | 1.1.2 | 1~25 | `1.1.2`（无页码） | 不可回溯 |
| **v4-pro** | 4.3.1 | 71~91 | `4.3.1, p.?` | 不可回溯（可见缺失） |

**这不是 flash 的问题**：v4-pro 在同一个 query 上也拿不到真实页码，只是它选择写 `p.?` 而不是编一个。
换句话说，**现在这条链路在 4.1.2 之外的小节上，从来就没有真正满足过 P0-05④。**

### 5.2 影响面（2D / 3D 更彻底）

| 形态 | 元素总数 | `source_page` 非空 | 填充率 |
|---|---:|---:|---:|
| anim_2d | 51 | 0 | **0%** |
| scene_3d | 19 | 0 | **0%** |
| **合计** | **70** | **0** | **0%** |

契约把 `source_page` 声明为「整数或 null」，所以填 null **不算契约违规**，我的清单也没判它挂
（否则会把「提示词缺陷」错记成「模型缺陷」）。但 P0-04② 要求「每条事实可回溯到页」，
**全填 null 等于完全不可回溯**。这条只作为 advisory 记录。

### 5.3 为什么这次才发现

任务 #2 的基线跑的是 4.1.2 小节，而 4.1.2 的真实页码恰好就是示例里的 76。
`real_examples` 与真实页码重合，把缺陷完全掩盖了。本次换到 4.3.1 / 5.1.1 / 1.1.2 才暴露。

### 5.4 建议的修法（属实现阶段，本次未改）

1. `_artifact_prompt` 里加一行，把 `context.pages` 显式给模型：
   `可选页码：71, 72, 73, 79, 80, 83…（source_ref / source_page 只能取这些值）`
2. 契约示例里的 `p.76` 换成**不指向具体页的占位**，或直接把示例的 `source_ref` 换成
   「本节真实页码」，避免模型照抄。
3. 把「页码 ∈ 检索命中页集合」做成 `parse_artifact_spec` 之外的**后校验**（现在 schema 只校验是字符串）。
4. 修完后用 `scripts/flash_quality_check.py --only ppt` 复跑，看 `source_ref 页码可回溯且真实` 是否转绿。

### G3 的精确数字 —— 注意：门禁口径不能只看「可解析率」

| 模型 | slide 总数 | 含可解析 `p.N` | **落在检索区间内** |
|---|---:|---:|---:|
| deepseek-flash（5 个 query） | 31 | **14（45%）** | **7（23%）** |
| deepseek-v4-pro（同 query 对照，ppt-4） | 5 | 0（0%） | 0（0%） |

逐 query 看：

| query 小节 | slide | 有 `p.N` | 真实 | 说明 |
|---|---:|---:|---:|---|
| 4.1.2 | 6 | 6 | **6** | 真实页恰好是 76，与示例重合 → 偶然全对 |
| 4.2.1 | 6 | 1 | 1 | 76 在该节区间内 → 偶然正确 |
| 5.1.1 | 6 | 0 | 0 | 完全省略页码 |
| 4.3.1 | 7 | 7 | **0** | 全部写 `p.76`，而该节真实页是 83~91 → **静默编造** |
| 1.1.2 | 6 | 0 | 0 | 完全省略页码 |

**这里有一个必须点明的口径陷阱**：
如果 G3 门禁按「含可解析 `p.N` 的 slide 占比」判定，flash 是 **45% > v4-pro 的 0%**，
会得出「flash 更好、门禁通过」的结论 —— **完全错误**。
flash 的可解析率之所以更高，正是因为它**照抄了契约示例里的 `p.76`**，
把「明显缺失」变成了「静默编造」。**编造一个错页码比不写页码更严重**（前者让学生查不到且不知道为什么，
后者至少暴露了缺失）。

**正确口径**是「页码落在检索命中区间内的 slide 占比」：flash 23%（7/31）、v4-pro 0%（0/5）。

> **给 G3 门禁的基线数字（产品经理要求量化）**：
> 建议门禁写成「**页码真实率 ≥ 30%**」（不是「不低于基线」）—— 理由：
> v4-pro 基线实测 **0%**（5 张 slide 全部不可解析），"不低于 0%" 等于没有门禁。
> 取 30% 是因为 flash 在「示例页码恰好命中」的小节（4.1.2 / 4.2.1）能拿到 100%，
> 在其余小节拿到 0%，两种情形混合后 23%；把 30% 设为下限可以**拦住"只在 4.1.2 上看起来对"的假通过**。
> **但这个基线只覆盖 1 个 query（5 张 slide）**，要作为正式门禁值需要与 G3 阶段二同批补到 ≥3 个 query。
按此口径，**两者都没变差（都远低于 95% 目标），也都不可接受**。
结论：**G3 是改动前就存在的缺陷，换档没有让它变差，但也没有让它变好；它不能作为「否决换档」的理由，
但必须作为独立缺陷单独排期**（与设计文档 Q-5「本次不修、只做可测量 + 不得更差」一致）。

## 六、两处对任务书的修正（读代码发现，不是推测）

### 6.1 2D 契约里没有 `t` 字段，「关键帧时间轴」检查的是 `step_index`

任务书写的是「2D 关键帧 `t` 是否单调递增、首帧是否为 0」。
`KeyframeStep` 的实际定义（`app/schemas/artifacts.py`）只有：

```python
class KeyframeStep(AstModel):
    step_index: int = Field(ge=0)
    narration: str
    source_ref: str = ""
    entities: list[Entity2D] = ...
```

**没有 `t`**。前端按 `step_index` 排序播放，所以检查项改成
「`step_index` 从 0 起严格递增」。实测 3/3 全过：`[0,1,2,3]`。

### 6.2 3D 机位名不是枚举，真正的风险是重名

任务书写的是「`camera` 预设名是否在合法枚举内」。实际 `CameraPreset.name` 是
`str = Field(min_length=1)`，**没有任何枚举**。`focus_camera` 的旁路实现是：

```ts
// frontend/src/lib/scene3d.ts
export function cameraPresetByName(tour, name) {
  const hit = tour.find((preset) => preset.name === name);
  return hit ?? null;
}
```

即**按名在 spec 自己的 `camera_tour` 里查找**。所以真正会坏的是**重名**（重名后第二个机位永远定位不到），
不是「值不在枚举内」。检查项改成「机位名非空且互不重复」。实测 3/3 全过，机位名分别是
`["全景","构造细部","入口视角"]` / `["港口全景","神庙与王权","码头与航线"]` / `["全景俯视","层级侧视","节点与证据"]`。

## 八、附带发现：`anim-1` 未生成产物的原因（检索问题，与模型无关）

query：`4.1.1 Malayan Union 的推进过程，做成动画演示`

结果：`grader_status = NO_MATCH`，`allowed_pages = []`，**0 次 LLM 调用**。

链路推演（读代码 + 实测值）：

1. `extract_section_code` 从问句里拿到 `scope = "4.1.1"`
2. `_search_with_widening` 先在 4.1.1 内检索，命中 **不足 `MIN_CANDIDATES=3` 条** → 逐级放宽到第 4 章 → 全库
3. 放宽后 `chunks[0]` 的 `section_code` 已经不是 `4.1.1` → `_grade` 里 `anchored = False`
4. 于是落到「实词命中率」判据：问句是中文、正文是马来文，`content_hit_ratio < 0.45` → `NO_MATCH`
5. `_decide_action` 见 `NO_MATCH` → `none` → 不生成产物

**这是检索/Grader 的既有行为，换成 v4-pro 也一样不会生成产物。**
它说明一条产品约束：**问句里带的中文描述性词汇越多，越容易把「点名了某小节」的强信号冲掉**。
本次把它保留为证据（不计入模型质量分母），另加了 `anim-1b`（4.1.2，切片充足）补齐 2D 的第 3 个有效样本。

## 十、如何重跑

```bash
cd <项目根>

# 完整三形态验证（12 个用例，11 个真实回合，约 3 分钟）
backend/.venv/Scripts/python.exe scripts/flash_quality_check.py

# 只复判 PPT 的页码项（修完提示词后用这条）
backend/.venv/Scripts/python.exe scripts/flash_quality_check.py --only ppt

# 只验 2D / 3D
backend/.venv/Scripts/python.exe scripts/flash_quality_check.py --only anim_2d,scene_3d

# 与 v4-pro 做归因对照（同一 query，只换模型）
backend/.venv/Scripts/python.exe scripts/flash_quality_check.py \
    --generator-model deepseek-v4-pro --only ppt --case-ids ppt-4

# 看全部参数
backend/.venv/Scripts/python.exe scripts/flash_quality_check.py --help
```

要点：

- **不动 `backend/.env`**：`--generator-model` 只在进程内包裹 `complete_json`，退出即失效；
  JSON 里记录的模型来自 `_post_json` 实际发出的 payload，所以一定是**真正生效**的那个
- 自动复用 `backend/data/profile/` 里已解析好的工作区，不重复入库
- 停手条件内置：连续 2 次降级 mock、或契约错误数递增 → 立刻中止并上报
- `--max-turns` 是硬上限，防止脚本失控烧 token

### 原始数据文件

| 文件 | 内容 |
|---|---|
| `flash-quality.raw.json` | 主批次 11 个回合的完整 spec + 质量清单 + 三层指标 |
| `flash-quality.anim2d-supplement.json` | 2D 补样（`anim-1` 未生成 + `anim-1b` 有效） |
| `flash-quality.v4pro-attribution.json` | v4-pro 在 `ppt-4` 上的归因对照（证明页码缺陷与模型无关） |
| `flash-quality.console.log` | 三批运行的完整控制台输出 |

> 注：`check_ppt` 的页码检查项在第一批跑完后**被修正过一次**（原实现把「解析不出页码」当作
> 「不适用」跳过，会让 v4-pro 的 `p.?` 被判成通过）。修正后**没有重新调用模型**，
> 而是用已落盘的 spec 离线重算，因此报告里的质量通过率与第一批控制台输出会不一致
> —— 以本报告（离线重算，口径更严）为准。
