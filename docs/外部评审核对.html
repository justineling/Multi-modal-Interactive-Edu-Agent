外部评审核对

一份外部 AI 对项目的架构审查（12 条问题 + 4 条改进口令）。逐条用代码核实过： 8 条成立、1 条部分成立、3 条是误判。误判的共同原因是——它只读了目录树和文档，没读实现。

先说公平话：这份点评整体质量不错。12 条里 8 条是真问题，其中「多教材章节碰撞」是我之前没注意到的、 而且已验证为真实缺陷。误判的 3 条都集中在「性能/并发/交互细节」——这三类恰恰是最需要看代码才能判断的。

一、三处明确误判（附代码证据）

❌ 误判 1：「SQLite 模式全表扫描反序列化 Embedding 会导致明显检索延迟」

点评原文：

「在 SQLite 模式下，如果没有向量索引加速，当工作区上传 2~3 本完整课本（数千个 chunks）时， 全表扫描反序列化 Embedding 会导致明显的检索延迟。」

实际情况：项目已经实现了它建议的方案。

点评建议项目现状（`backend/app/db/vector_store.py`）
「维护按 workspace_id 懒加载的内存级 NumPy float32 归一化矩阵缓存」 ✅ 已有：_matrix_cache: dict[str, tuple[list[str], np.ndarray]]（第 110 行）
「利用矩阵点乘 np.dot 将余弦相似度计算压缩到 1~2 毫秒」 ✅ 已有：np.vstack(vectors) 建矩阵（第 299 行），import numpy as np（第 19 行）
「全表扫描反序列化」 ❌ 不存在：向量在启动时一次性加载进内存（日志 vector_store_loaded count=1170），检索时不再反序列化

我实测了这个规模的实际耗时（1170 个切片 × 1536 维，即启动日志里的真实数量）：

NumPy 矩阵点乘（1170×1536）: 0.661 ms/次
# 含 argpartition 取 Top-8

0.66 毫秒，不是「明显延迟」。点评建议的优化已经做完了。

唯一成立的部分：「SQLite FTS5 + RRF」确实没做——现在的 BM25 是 Python 侧算的，不是 SQLite 全文索引。 但这是**有意的取舍**：SQLite FTS5 的中文分词支持很弱，用它反而会降低中文检索质量。 当前实现是「BM25（Python）+ 向量（NumPy）」双通道加权融合，效果比 FTS5 好。

❌ 误判 2：「SSE 断连时后台仍会跑完整个 JSON 生成，白白浪费 API 额度」

点评原文：

「如果用户在流式输出中途刷新页面或中断请求，`chat_stream.py` 若未及时捕获客户端断开信号并取消后台正在跑的 Artifact 生成协程，后台仍会继续调用大模型跑完整个 JSON 生成，白白浪费 API 额度。」

实际情况：已经处理，而且处理得比它建议的更细致。

backend/app/services/agent_engine.py:808-821：

# 断连/异常时取消未完成的产物分支：httpx 请求随之取消（CancelledError 是
# BaseException 不是 Exception，见 IMPL-NOTES E12 ⑤）
finally:
    if work_task is not None and not work_task.done():
        work_task.cancel()
        work_task.add_done_callback(_reap_task)
        with contextlib.suppress(asyncio.CancelledError):
            await work_task

三点它没看到：

  1. work_task.cancel() 取消的正是产物生成协程，httpx 请求会随之取消，不会继续烧 token
  2. add_done_callback(_reap_task) 是它建议里没提的——不加会打 Task exception was never retrieved
  3. 注释明确写了「不得改成 except Exception」——因为 CancelledError 继承自 BaseException，写成 except Exception 会让整个取消机制静默失效

这一条已记在 docs/00-源文档/IMPL-NOTES.md E12 ⑤，原文写着「这两条是并行方案成立的前提，不是实现细节」。

❌ 误判 3：「学生看到 [p.94] 却无法点击，页码锚点价值停留在纯文字标签上」

实际情况：可以点击，但展开的不是 PDF 原貌（这一点它说对了）。

frontend/src/components/chat/CitationList.tsx:45：

const chunks = await listChunks(documentId, { section_code: sectionCode, limit: 3 });

每个引用 chip 都能点开，展开的是该章节的切片原文（3 条），不是"纯文字标签"。 界面上还写着「（点击展开教材原文）」。

但它的核心建议是对的：展开的是**文本**，不是 **PDF 页面图**。 学生想看"课本第 94 页长什么样"（包括插图、版式）确实做不到。 做 PDF 预览器是有价值的改进——只是它的"现状描述"错了（不是不可点击，是可点击但只给文本）。

二、部分成立的两条

⚠️ 「历史消息无法一眼看出对应哪个 Artifact 的哪个版本」

能看出，但不能跳转。MessageBubble.tsx:134-139 会渲染 artifact_id 与 v{version} 的文字标记，所以"哪个版本"是可见的；但它是纯文字，点击不能把右侧画布切回那个版本。

所以「产物快照卡片 + 点击跳转」这个建议成立，只是"无法一眼看出"这个描述不准确。

⚠️ 「文档解析只显示笼统的 processing」

有百分比，但没有阶段。DocumentCard.tsx:29 显示 解析中 ${progress}%， 不是笼统的 "processing"。但确实是单一百分比，没有「解析目录树 → 切分章节 → 构建向量」的阶段划分。

建议的「分阶段进度条」成立，但需要后端把 progress 拆成阶段字段——这是一次契约变更。

三、成立的八条（我认可，且验证过）

#问题我的核实结果优先级
1 多教材章节号碰撞 已验证为真缺陷。retriever.retrieve() 只接 workspace_id， search_similar(workspace_id, ..., section_prefix=...) 不带 document_id。 同一工作区传 Form 4 + Form 5（都有 Bab 4 → 4.1）会混召回。 这条我之前没注意到，是最有价值的发现。 高
2 QuizLayout 开环 已验证：QuizLayout.tsx 只有 useState + onClick，无 fetch、无 store， 作答结果不回流。"答错 → 一键用动画拆解这题"是合理的产品补全。 中
3 引用看不到 PDF 原貌 成立（见上文误判 3 的修正）。需要后端加 GET .../documents/{id}/raw 流式端点 + 前端 PDF 预览抽屉。 中
4 2D/3D 坐标靠 LLM 硬算 成立。Entity2D.x/y 是归一化 0~1000×0~600，Node3D.position 是 3 元组， 全靠模型算。小模型容易重叠/穿模。但严重程度需要真实 GPU 上看一次再定—— 如果实际很少穿模，改语义布局（要动契约）的性价比就不高。 中
5 JSON Patch 数组下标脆弱 成立。LLM 输出 /slides/2 表示第 3 页，确实容易错。项目已有 node_id （slide-1/slide-2）但只用于 payload 内部，路径仍用下标。 「按 ID 寻址」（/slides[node_id=slide-2]）是合理演进。 中
6 并行下右侧长白屏 成立。产物必须等完整 AST 才 yield "spec"，期间右侧是空态。 实际约 10 秒（它说的 6~12 秒偏大，实测产物阶段 10.1s）。 「骨架屏事件」是低成本的体验改进。 中
7 窄屏布局未优化 成立。SplitWorkspace.tsx 里 grep 不到 matchMedia/innerWidth/useMediaQuery， 左右双栏写死并排。 中
8 只支持 PDF / 无 Word-PPT 解析 成立，但不是"未实现"，是"从未规划"——PRD 只要求 PDF。 不过对真实用户（老师手上可能是 .docx/.pptx）确实是门槛。 低
