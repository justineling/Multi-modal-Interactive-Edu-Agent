五层测试各管什么

层数量管什么跑多快
契约测试~30 AST 结构对不对、非法输入是否被拒、注入防护 毫秒级
单元测试~80 单个函数的行为：补丁引擎、检索打分、章节解析、路由 毫秒级
API 测试~40 HTTP 端点：状态码、响应结构、SSE 事件顺序 秒级
验收测试53 PRD 的 12 条 P0 逐条验收（QA 写的，是验收基准） 秒级
端到端38 项 真实起服务、真实上传 PDF、真实 SSE 流 十几秒
前端测试153 SSE 解析、JSON Pointer、指纹、坐标换算、布局渲染 3 秒

金字塔原则：越底层的测试越多越快，越顶层越少越慢。 如果发现自己在写大量端到端测试，说明底层抽得不够——大部分逻辑应该能在函数级测掉。

怎么跑

后端

# 全量（约 30 秒）
cd backend
.venv\Scripts\python.exe -m pytest tests -q

# 只跑某个文件
.venv\Scripts\python.exe -m pytest tests/test_patch_engine.py -q

# 只跑某个用例（名字模糊匹配）
.venv\Scripts\python.exe -m pytest tests -k "subtree" -q

# 失败时显示详细断言
.venv\Scripts\python.exe -m pytest tests -q -vv

# 只跑上次失败的
.venv\Scripts\python.exe -m pytest tests --lf

前端

cd frontend

npm test                # 单跑一次
npm run test:watch      # 监听模式，改文件自动重跑
npm test -- sse         # 只跑 sse 相关

npm run typecheck       # 只做类型检查，不构建（快）
npm run build           # 类型检查 + 构建

端到端

# 终端 1：起服务
cd backend
.venv\Scripts\python.exe -m uvicorn app.main:app --port 8123

# 终端 2：跑冒烟脚本
cd backend
.venv\Scripts\python.exe ../scripts/e2e_smoke.py

输出是 38 项 PASS/FAIL 清单，最后一行汇总。任何 FAIL 都会打印实际值。

怎么写一个新测试

后端测试的骨架

backend/tests/conftest.py 已经提供了现成夹具：

夹具给你什么
client已接好临时数据库的 HTTP 客户端
session异步数据库会话
sample_pdf_path生成的 113 页样本 PDF 路径
ppt_spec / anim_spec / scene_spec三种 AST 的合法样例

写一个测试：

async def test_my_feature(client):
    """一句话说明这个测试验证什么。"""
    resp = await client.post("/api/workspaces", json={"title": "测试"})
    assert resp.status_code == 200
    assert resp.json()["code"] == "OK"

前端测试的骨架

import { describe, expect, it } from "vitest";

describe("模块名", () => {
  it("具体行为描述", () => {
    expect(yourFunction(input)).toBe(expected);
  });
});

什么值得写测试

值得写不值得写
  • 纯函数（有明确输入输出）
  • 边界条件（空数组、null、超长）
  • 曾经出过 bug 的地方（回归）
  • 契约校验（正例 + 反例）
  • 纯展示组件（除非有交互逻辑）
  • 框架自带的行为
  • "能跑就行"的胶水代码
  • 需要大量 mock 才能测的东西（通常是设计问题）

调试的四个入口

入口一：后端日志

所有关键节点都有 log_event()，带 turn_id 可以串起一整轮：

# 终端里看
uvicorn app.main:app --reload --log-level debug

# 或改 .env 的 LOG_LEVEL=DEBUG

典型输出：

retrieval_done    turn_id=abc123 grader_status=SYLLABUS_MATCH top_score=0.5916
modality_route    turn_id=abc123 artifact_type=ppt user_override=false
artifact_created  turn_id=abc123 artifact_id=8df752fd version=1

用 turn_id grep 一遍，就能看到这一轮完整的执行轨迹。

入口二：直接 curl API

前端表现异常时，先用 curl 排除是前端还是后端的问题：

# 健康检查
curl http://127.0.0.1:8000/api/health

# 看 SSE 原始输出（-N 关闭缓冲）
curl -N -X POST http://127.0.0.1:8000/api/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"workspace_id":"xxx","query":"4.1 讲了什么","mode":"syllabus_strict"}'

能看到完整的事件流，逐行 event: xxx / data: {...}。

入口三：浏览器控制台

看什么怎么用
Console红色报错、console.log 输出
Network看 /api/chat/stream 的请求体、响应头、流式内容
React DevTools看组件树和 props，确认数据有没有传到位
Elements看 DOM 结构和实际生效的 CSS

入口四：断点

后端：在 VS Code 里配 launch.json：

{
  "name": "FastAPI",
  "type": "debugpy",
  "request": "launch",
  "module": "uvicorn",
  "args": ["app.main:app", "--reload"],
  "cwd": "${workspaceFolder}/backend"
}

前端：浏览器 DevTools 的 Sources 面板，直接点行号下断点，支持查看变量和单步。

调试 SSE 时最有用的一招：在 api/sse.ts 解析出每个事件的地方加一行 console.log("[SSE]", event, data)。所有事件按顺序打印出来， 一眼就能看出是"事件没到"还是"到了但没处理"。

常见错误对照表

现象大概率原因去哪看
401/403 或 CORS 报错 后端没起，或 CORS 白名单没含前端地址 config.py 的 CORS_ORIGINS
前端一直"生成中" SSE 没收到 turn_end（异常路径漏发） chat_stream.py 的兜底逻辑
画布白屏 spec 字段缺失导致渲染器抛异常 浏览器 Console；ArtifactHost 的 ErrorBoundary
点画布没反应 锚点没设置成功，或点击事件没绑定 React DevTools 看 store 的 anchor
patch 后整页都变了 update_node 被写成整体替换（没做 merge） useArtifactPatch.ts
上传后目录树只有 Page 1/2/3 章节号识别失败，走了 page_fallback pdf_parser.py 的正则
什么问题都说"课本未覆盖" 实词门槛太高，或 embedding 没生成 retriever.py + text_signals.py
无关问题也能答 门槛太低，或 BM25 归一化用了相对值 config.py 的 GRADER_CONTENT_HIT_MIN_RATIO
两次生成结果不一样 代码里混进了 random / 内置 hash() mock_generator.py、embedding.py
并发 patch 报 500 乐观锁没翻译成 409 api/artifacts.py 的 IntegrityError 捕获
重启后数据没了 SQLite 相对路径锚定问题（CWD 不同） 固定 cd backend 再启动
3D 白屏 @react-three/fiber 装成 v8（不兼容 React 19） package.json 版本

三条测试纪律

① 关键断言要独立实现。 用 patch_engine.assert_only_subtree_changed 去验证补丁引擎，等于自己验自己。 测试侧应该重写一份独立实现。项目的 tests/acceptance_support.py 就是这么做的。

② 失败的测试是资产，不要为了全绿而删断言或放宽条件。 测试红了说明发现了问题。改成"能过"的样子，等于把问题藏起来。 正确做法是：修源码让它变绿，或者明确标注 xfail 并写清原因。

③ 正例和反例必须成对出现。 "相关问题能检索到"和"无关问题必须拒绝"要一起测。 只测前者，阈值调到极低也能全绿；只测后者，全判 NO_MATCH 也能全绿。 成对测试才能锁住真实行为。
