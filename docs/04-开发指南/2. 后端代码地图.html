推荐阅读顺序

不要按字母顺序读，会迷路。按这个顺序，每一步都建立在前一步之上：

① config.py
先知道有哪些可调参数
↓
② schemas/artifacts.py
核心契约，理解数据结构
↓
③ db/models.py
数据怎么存
↓
④ services/retriever.py
最有技术含量的一块
↓
⑤ services/agent_engine.py
主流程编排
↓
⑥ api/chat_stream.py
怎么包装成 HTTP

根目录与配置

文件职责关键内容
app/main.py FastAPI 入口 挂载 3 个 router、注册全局异常处理器、lifespan 里初始化 DB 与向量存储、CORS
app/config.py 所有配置项 Settings 类（pydantic-settings），从 .env 读。含 DB URL、模型名、各种阈值
app/errors.py 错误码枚举 ErrorCode（21 个码）+ AppError 异常类。前端 api/client.ts 镜像同一份
app/logging_conf.py 日志配置 log_event() 结构化日志，带 turn_id 可追踪整条链路

先读 config.py 的价值：它告诉你这个系统有哪些"旋钮"。 看一遍你就知道哪些行为可以调（阈值、上限、模型名），哪些是硬编码在逻辑里的。

db/ 数据层

文件职责关键函数/类
db/models.py 7 张表的 SQLAlchemy 声明 Workspace / Document / DocumentChunk / ChunkVector / Artifact / ArtifactVersion / Message
db/session.py 异步连接池 get_session()（请求级事务依赖）、init_db()、dispose_engine()
db/vector_store.py 向量存取抽象 EmbeddingStore 协议 + MemoryVectorStore + PgVectorStore + build_vector_store()
db/repository.py 数据访问封装 apply_artifact_patch()（版本追加 + 快照前移）、append_artifact_version()、各类 require_* 查询

repository.py 是唯一允许写 SQL 的地方。 API 层和服务层都不该直接 session.execute()。 这样做的好处是"改查询逻辑只改一处"，坏处是 repository 会变长——但比散落各处好。

schemas/ 契约层

文件职责关键内容
schemas/artifacts.py 三种 JSON AST SlideDeckSpec / Keyframe2DSpec / SceneGraph3DSpec，以及基类 AstModel（含注入防护）
schemas/patch.py 补丁协议 PatchOp / PatchRequest / NODE_PATH_RE 正则
schemas/chat.py SSE 事件契约 8 个 Event 类 + encode_sse() + SSE_EVENT_MODELS + EVENT_ORDER
schemas/api.py HTTP 出参 DTO WorkspaceOut / DocumentOut / TocNodeOut / ChunkOut / ArtifactOut / ArtifactVersionOut
schemas/common.py 通用工具 ApiResponse（统一响应包装）、canonical_json()、canonical_tree()

改这些文件等于改前后端契约。必须同步改前端 src/types/*.ts， 否则类型对不上。规则见 DSL 契约 · 四条铁律。

services/ 服务层

这是项目的主体，10 个文件。按数据流顺序列：

知识管线（上传时跑）

文件职责关键点
pdf_parser.py PDF → 章节结构 + 逐页文本 正则识别 Chapter 4/4.1/4.1.2；识别失败走 page_fallback；体检在落盘前做
chunker.py 按章节切片 页面归属排他（切片不重叠）、碎块合并（<200 字并入前块）、chunk_index 全局连续
embedding.py 文本 → 向量 本地确定性实现：blake2b 哈希到 1536 维桶 + L2 归一化。禁止 random/内置 hash()
tasks.py 解析任务管理 asyncio.Task + 0.3 秒进度落库 + 可取消。不引入 Celery/Redis

检索管线（提问时跑）

文件职责关键点
retriever.py 混合检索 + 覆盖判定 章节过滤 → BM25 + 余弦 → 加权融合 → 实词命中率门槛 → 三态判定
text_signals.py 实词提取 中文 bigram + 虚词剔除 + 套话过滤；has_explicit_section_reference() 判章节引用

生成管线（提问时跑）

文件职责关键点
router.py 形态路由 显式 override 优先 → 关键词打分 → 默认 PPT。产出人话 reason
llm_client.py 模型调用 httpx 直连 OpenAI 兼容端点；JSON 抽取（剥 ```json 围栏）；校验失败回灌重试
mock_generator.py 演示模式生成器 纯函数，同输入同输出。从检索切片抽句填充模板，不是纯占位符
agent_engine.py 主流程编排 stream_turn() 异步生成器，按序 yield 8 类事件；_create_artifact_stream / _patch_artifact_stream
patch_engine.py 补丁执行 apply_patch()：deepcopy → 定点写入 → 校验 → 回滚。含 fingerprint() 与 assert_only_subtree_changed()

为什么 agent_engine.py 是最大的文件？因为它是编排层， 天然要协调所有服务。如果它变得难读，正确做法是往下抽服务，而不是在它内部加 if 分支。

api/ 接口层

文件职责端点
workspaces.py 工作区、文档、上传、目录树、切片 12 个（含 GET /api/health 在 main.py）
chat_stream.py SSE 流式对话 + 非流式 POST /api/chat/stream、POST /api/chat
artifacts.py 产物 CRUD、版本、补丁 5 个

API 层只做三件事：解析请求 → 调服务 → 包装响应。不写业务逻辑。

tests/ 测试

文件测什么
conftest.py夹具：临时 SQLite、HTTP 客户端、三种 AST 样例、样本 PDF
test_contracts.py三种 AST 的正反例、注入防护
test_patch_engine.py5 种 op、字节级不变断言
test_pdf_parser.py章节识别、page_fallback、异常 PDF
test_retriever.py混合检索、Top-5 同章、workspace 隔离
test_router.py10 条预置问句路由准确率
test_mock_determinism.py跨进程 AST 指纹一致（防 PYTHONHASHSEED 陷阱）
test_api_smoke.pySSE 8 事件顺序、版本自增
test_acceptance_p0_*.pyQA 写的 P0 验收测试（53 条），逐条对应 PRD
test_regression_*.py修过的 bug 的回归用例

读测试比读源码快。想知道某个函数怎么用，去看它的测试用例—— 测试里一定有最典型的调用方式，而且断言会告诉你"正常行为应该是什么"。
