1一次提问的完整旅程

这是整套文档里最重要的一篇。我们把"用户按回车"这一秒内发生的事，拆成 10 站逐一追踪。 读完这篇，你就知道每个文件为什么存在、改功能该去哪个文件。

怎么读这篇：建议同时打开代码编辑器，跟着每一站的文件路径去看真实代码。 只看文档不动手，很容易"读懂了但记不住"。每一站我都标了「打开哪个文件、找哪个函数」。

十站路线
  1. 浏览器：按下回车
  2. 前端：组装请求
  3. 网络：SSE 连接建立
  4. 后端：进入 API 层
  5. 引擎：开始编排
  6. 检索：找到课本片段
  7. 路由：决定出什么形态
  8. 生成：填 JSON AST
  9. 落库：写两张表
  10. 回流：前端重渲染

第 1 站 · 浏览器：按下回车

打开：frontend/src/components/chat/Composer.tsx

输入框组件监听键盘事件。按下回车（且没有 Shift）时，它做两件事：

  1. 取输入框的文本
  2. 取当前锚点（如果用户点过画布上的元素，输入框上方会有个 chip）

然后调用 store 里的发送方法。注意它自己不直接发请求——组件只管交互，发请求是 hook 的事。

// 简化后的逻辑
function handleSubmit() {
  if (!text.trim()) return;
  onSend(text, anchor);        // anchor 可能是 null
  setText("");               // 清空输入框
}

为什么组件不直接发请求？因为"发请求"涉及 SSE 流、事件分发、状态更新、 取消与重连，逻辑很重。把它抽到 hook（useChatStream）里，组件才能保持简单。 这是 React 的常规分层：组件管"长什么样"，hook 管"做什么"。

第 2 站 · 前端：组装请求

打开：frontend/src/hooks/useChatStream.ts

这个 hook 是整个前端的数据中枢。它要做四件事：

动作说明
幂等守卫用 AbortController + in-flight ref，防止 StrictMode 双挂载导致重复请求
乐观更新立刻把用户消息 push 到 store，界面马上显示，不等后端
建占位消息建一条空的 assistant 消息，标记 streaming: true，后续 token 往这里追加
发起流调 api/sse.ts 的 streamChat()

请求体长这样：

{
  "workspace_id": "86f98c81-...",
  "query": "4.1 Malayan Union 对苏丹的影响",
  "mode": "syllabus_strict",
  "anchor": null,
  "artifact_type_override": null,
  "history_limit": 8
}

anchor 是这一站最关键的字段。如果用户点过画布，这里会有 {artifact_id, node_path, section_code, page, node_label}。 后端看到它就会：① 把检索锁定在那个小节 ② 走 patch 而不是新建产物。 一个字段决定了两条完全不同的执行路径。

第 3 站 · 网络：SSE 连接建立

打开：frontend/src/api/sse.ts

这里用 fetch + ReadableStream 手写了一个 SSE 解析器。 为什么不用浏览器内置的 EventSource？因为它不支持 POST。

解析器的工作是：把网络上传来的字节流，切成一个个「事件」。网络传输是分片的， 一个事件可能被切成两半到达，所以要维护一个 buffer：

buffer += 新到达的文本
blocks = buffer.split("\n\n")     // 空行分隔事件
buffer = blocks.pop()                // 最后一块可能不完整，留着

for (block of blocks) {
  解析 event: 和 data: 行 → 回调出去
}

解析出的事件会通过回调交给 useChatStream 分发。

第 4 站 · 后端：进入 API 层

打开：backend/app/api/chat_stream.py → 函数 chat_stream()

FastAPI 收到 POST 请求，先做三件事：

  1. Pydantic 校验请求体。字段缺失或类型不对，直接返回 400，不会进业务逻辑。
  2. 生成 turn_id（复用 request_id），贯穿整个回合的日志追踪。
  3. 返回 StreamingResponse，把生成器包成 SSE 流。

这里有个不显眼但重要的设计：队列 + 超时保活。 如果直接 async for 转发生成器，asyncio.wait_for 超时会取消正在等待的 __anext__()，把整个生成器关掉。所以改成「后台任务写队列、响应协程读队列」， 超时就发一行 : ping 注释，不干扰生成。

第 5 站 · 引擎：开始编排

打开：backend/app/services/agent_engine.py → AgentEngine.stream_turn()

这是整个后端的大脑。它是一个异步生成器——每完成一个阶段就 yield 一个事件， 事件被上层转成 SSE 推给前端。

执行顺序严格固定：

yield "turn_start", TurnStartEvent(...)

result = await retriever.retrieve(query, workspace_id, anchor)
yield "retrieval", RetrievalEvent(...)

decision = router.route(query, result, override)
yield "modality_decision", ModalityDecisionEvent(...)

async for chunk in self._compose_reply_stream(...):
    yield "token", TokenEvent(delta=chunk)

yield "artifact", ArtifactEvent(...)
yield "citations", CitationsEvent(...)
yield "turn_end", TurnEndEvent(...)

为什么用生成器而不是普通函数？因为要边算边发。用户不用等全部算完才看到文字， 第一个 token 出来就推过去了（这就是 TTFT 只有几毫秒的原因）。

第 6 站 · 检索：找到课本片段

打开：backend/app/services/retriever.py → Retriever.retrieve()

四步（详细算法见 检索与路由）：

  1. 章节精确过滤

    如果 query 里有章节号（4.1），或者 anchor 带了 section_code， 先用 SQL 捞出该节所有切片。这是"目录树锚定"的实现。

  2. 双通道打分

    BM25（词面匹配）+ 向量余弦（语义相似）。两个通道各有盲区，互补。

  3. 加权融合取 Top-8

    0.35×bm25 + 0.45×cosine + 0.15×section_bonus + 0.05×page_bonus

  4. 覆盖判定

    调 text_signals.content_words() 提实词，算命中率。低于 0.45 → NO_MATCH。

产出是一个 RetrievalResult，含 grader_status、chunks、top_score、section_scope。

第 7 站 · 路由：决定出什么形态

打开：backend/app/services/router.py → route()

判断该出 PPT / 2D / 3D。优先级：

  1. 用户显式指定（artifact_type_override）→ 直接用，不判断
  2. 否则按关键词打分：空间类 → 3D，过程类 → 2D，离散类 → PPT
  3. 都没命中 → 默认 PPT

返回 {artifact_type, reason, user_override}。reason 会直接显示给用户， 所以必须是人话，不能是 "matched_keyword: impact" 这种。

第 8 站 · 生成：填 JSON AST

打开：backend/app/services/agent_engine.py → _create_artifact_stream() / _patch_artifact_stream()

这里分两条路：

路径 A：新建产物（无锚点）

  1. 组装提示词：检索到的课本片段 + 目标 AST 的 JSON Schema
  2. 调 llm_client.chat_json()（或 mock_generator，演示模式下）
  3. Pydantic 校验 → 失败则把错误回灌给模型重试（最多 3 次）
  4. 全失败 → 降级到 mock，保证用户不会空手

路径 B：增量补丁（有锚点）

  1. 从数据库读出当前 artifact 的 spec
  2. 把 spec 摘要 + 锚点 + 用户问题一起给模型，要求它输出 PatchOp 数组
  3. 调 patch_engine.apply_patch() 应用补丁
  4. 校验通过后写新版本

路径 B 的关键约束：update_node 的 payload 只带被改字段。 前端必须做字段级 merge。这一条写错，渲染器当场崩——详见 增量补丁。

第 9 站 · 落库：写两张表

打开：backend/app/db/repository.py

新建或 patch 都要写两张表：

表写什么
artifacts更新 spec_json（最新版）+ version +1
artifact_versionsINSERT 一行快照（append-only，绝不 UPDATE）

另外每轮对话结束还要写两条 messages（user + assistant），供刷新后恢复会话。

写版本快照必须 copy.deepcopy。SQLAlchemy 的 JSON 类型不追踪嵌套原地修改。 如果快照和 artifact.spec_json 共享同一个 dict 对象，后续修改 artifact 会连带改到历史行。

第 10 站 · 回流：前端重渲染

打开：frontend/src/hooks/useChatStream.ts 的事件分发 → store/useWorkspaceStore.ts

每个 SSE 事件对应一个 store 更新动作：

事件store 动作界面变化
turn_startbeginStreaming()输入框禁用，显示"生成中"
tokenappendToken(delta)文字逐字出现
retrieval存 grader 状态与命中片段引用可展开
modality_decision存路由理由显示"为什么生成 PPT"
artifactupsertArtifact()右侧画布渲染产物
citations挂到消息上底部出现引用列表
turn_endendStreaming()输入框恢复可用

Zustand 的状态一变，订阅它的组件自动重渲染。右侧 ArtifactHost 按 spec.type 策略分发到对应渲染器，画面就出来了。

到这一步，一次提问就完整走完了。你现在应该能回答这些问题：

  • 想改"为什么生成 PPT"那句话的文案 → 改 router.py
  • 想改 PPT 某一页的样式 → 改 components/canvas/layouts/*.tsx
  • 想改引用页码的排序 → 改 agent_engine._build_citations
  • 想加一个新的 SSE 事件 → 改 schemas/chat.py + useChatStream.ts 两处
