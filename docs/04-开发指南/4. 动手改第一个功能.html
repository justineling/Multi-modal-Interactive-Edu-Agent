4动手改第一个功能

三个实战，从易到难：改后端逻辑 → 改前端界面 → 加一个新字段贯穿全链路。每个都有完整步骤和验证方法。

先决条件：你已经按 环境搭建 跑起来了， 并且 pytest 和 npm test 都是绿的。改动前先确认基线是绿的—— 否则改完出错你分不清是自己改坏的还是本来就坏的。

三个实战
  1. 实战 A：改后端路由规则（约 10 分钟）
  2. 实战 B：给 PPT 加一个复制按钮（约 20 分钟）
  3. 实战 C：加一个字段贯穿全链路（约 40 分钟）
  4. 改代码的五条纪律

实战 A：改后端路由规则

目标：让问句里出现"地图"时也路由到 3D 场景（现在只有"结构/布局"等词才触发）。

步骤 1：找到关键词表

打开 backend/app/services/router.py，找到空间类关键词的列表。大概长这样：

SPATIAL_KEYWORDS = (
    "结构", "布局", "内部", "剖面",
    "相对位置", "方位", ...
)

步骤 2：加关键词

SPATIAL_KEYWORDS = (
    "结构", "布局", "内部", "剖面",
    "相对位置", "方位",
    "地图", "地形", "疆域",   # ← 新增
)

步骤 3：改理由文案（重要）

同一文件里有个 reason 的拼接逻辑。原来可能是：

reason = f"问句命中「{hit}」，涉及空间结构，3D 场景更能建立空间感"

加了地图类词后，这个理由对"地图"就不太贴切了。改成更通用的表述：

reason = f"问句命中「{hit}」，涉及空间关系或地理分布，3D 场景比平面图更直观"

理由文案为什么重要？它会直接显示给用户，是用户判断"这个形态对不对"的依据。 写 "matched_keyword: map" 用户看不懂；写人话用户才能反馈"不对，我要 PPT"。

步骤 4：补测试

打开 backend/tests/test_router.py，找到预置问句列表，加一条：

{
    "query": "马来半岛的地图各州分布是怎样的",
    "expected": "scene_3d",
},

步骤 5：跑测试验证

cd backend
.venv\Scripts\python.exe -m pytest tests/test_router.py -q

应该是全绿。如果挂了，看断言信息里期望什么、实际什么。

步骤 6：真机验证

重启后端（--reload 会自动重启），前端发一句"马来半岛的地图各州分布"，看画布是否出 3D 场景、理由是否是新的文案。

步骤 7：提交

git add backend
git commit -m "feat(router): 地图/地形/疆域类问句路由到 3D 场景"

实战 B：给 PPT 加一个复制按钮

目标：画布工具栏加一个「复制为 Markdown」按钮，把当前 PPT 的所有页面文字复制到剪贴板。

步骤 1：先想清楚数据从哪来

PPT 的 spec 存在 store 里。要拿到它，用选择器：

import { useWorkspaceStore, selectActiveArtifact } from "@/store/useWorkspaceStore";

const artifact = useWorkspaceStore(selectActiveArtifact);

为什么用选择器而不是 useWorkspaceStore(state => state)？ 后者订阅整个 store，任何状态变化都会重渲染这个组件。选择器只订阅需要的那一块。

步骤 2：写转换函数

新建 frontend/src/lib/exportMarkdown.ts：

import type { ArtifactSpec, SlideDeckSpec } from "@/types/artifact";

export function slideDeckToMarkdown(spec: SlideDeckSpec): string {
  const lines: string[] = [`# ${spec.topic}`, ""];

  spec.slides.forEach((slide, i) => {
    lines.push(`## ${i + 1}. ${slide.title}`);
    if (slide.subtitle) lines.push(`> ${slide.subtitle}`);

    slide.bullets.forEach((b) => lines.push(`- ${b}`));

    if (slide.comparison_left && slide.comparison_right) {
      lines.push("| 左 | 右 |", "|---|---|");
      const n = Math.max(slide.comparison_left.length, slide.comparison_right.length);
      for (let j = 0; j < n; j++) {
        lines.push(`| ${slide.comparison_left[j] ?? ""} | ${slide.comparison_right[j] ?? ""} |`);
      }
    }

    if (slide.speaker_notes) lines.push("", `> 讲解：${slide.speaker_notes}`);
    lines.push("", `*出处：${slide.source_ref}*`, "");
  });

  return lines.join("\n");
}

步骤 3：在工具栏加按钮

打开 frontend/src/components/canvas/CanvasToolbar.tsx，加一个按钮：

const handleCopy = async () => {
  if (!artifact || artifact.spec.type !== "ppt") return;

  const md = slideDeckToMarkdown(artifact.spec);
  try {
    await navigator.clipboard.writeText(md);
    setToast("已复制到剪贴板");
  } catch {
    setToast("复制失败，请检查浏览器权限");
  }
};

<button onClick={handleCopy} disabled={artifact?.spec.type !== "ppt"}>
  复制为 Markdown
</button>

artifact.spec.type !== "ppt" 这个判断不能省。 TypeScript 会用它做类型收窄——判断之后 artifact.spec 才被识别为 SlideDeckSpec，才能访问 .slides。不判断会编译报错。

步骤 4：写单元测试

新建 frontend/src/lib/exportMarkdown.test.ts：

import { describe, expect, it } from "vitest";
import { slideDeckToMarkdown } from "./exportMarkdown";

describe("slideDeckToMarkdown", () => {
  it("输出包含标题与要点", () => {
    const md = slideDeckToMarkdown({
      type: "ppt",
      topic: "测试主题",
      slides: [{
        node_id: "slide-1", layout: "bullet_points",
        title: "第一页", subtitle: null, bullets: ["要点一"],
        comparison_left: null, comparison_right: null,
        timeline_items: null, quiz_questions: null,
        speaker_notes: "讲解", source_ref: "p.1",
      }],
    });
    expect(md).toContain("# 测试主题");
    expect(md).toContain("- 要点一");
  });
});

步骤 5：验证

cd frontend
npm test
npm run build

然后真机点一下按钮，粘贴到别处看效果。

步骤 6：提交

git add frontend
git commit -m "feat(canvas): PPT 支持复制为 Markdown"

实战 C：加一个字段贯穿全链路

目标：给 PPT 每一页加一个 difficulty 字段（"basic" | "advanced"）， 前端用不同颜色角标显示。这个实战走完契约扩展的完整流程。

只能加可选字段，不能改已有字段。历史版本的 spec 是 append-only 的， 改了已有字段的语义，所有旧数据都会失效且无法批量迁移。

步骤 1：后端契约加字段

backend/app/schemas/artifacts.py 的 SlideNode：

difficulty: Literal["basic", "advanced"] | None = None
# 必须有默认值 None，否则历史 spec 校验失败

步骤 2：前端类型同步

frontend/src/types/artifact.ts 的 SlideNode：

difficulty: "basic" | "advanced" | null;

步骤 3：让 mock 生成器产出它

backend/app/services/mock_generator.py 里生成 slide 的地方，加一行：

difficulty = "basic" if i < len(slides) // 2 else "advanced"

不加这行，演示模式下这个字段永远是 null，你看不到效果。

步骤 4：前端渲染

打开 frontend/src/components/canvas/SlideRenderer.tsx，在页面角落加角标：

{slide.difficulty && (
  <span className={slide.difficulty === "advanced"
    ? "badge-advanced" : "badge-basic"}>
    {slide.difficulty === "advanced" ? "进阶" : "基础"}
  </span>
)}

步骤 5：补三层测试

层测什么
test_contracts.py带 difficulty 的 spec 能通过校验；传非法值被拒
test_mock_determinism.py两次生成都带同一个 difficulty 值
SlideRenderer.test.tsxdifficulty: "advanced" 时渲染出「进阶」角标

步骤 6：全量回归

cd backend && .venv\Scripts\python.exe -m pytest tests -q
cd ../frontend && npm test && npm run build

三条都绿才算完成。任何一条红，说明改动破坏了某个已有假设。

步骤 7：验证旧数据兼容

这是最容易被忘的一步。找一个改动前生成的产物，打开看是否还能正常渲染 （旧 spec 里没有 difficulty 字段，应该显示为无角标，而不是报错）。

为什么这一步重要？因为版本历史是 append-only 的，旧 spec 永远存在。 新代码必须能读旧数据——这是"只加可选字段"规则的价值所在。

改代码的五条纪律

  1. 先跑测试确认基线是绿的

    不然改完出错你分不清是谁的问题。

  2. 只加不改（对契约而言）

    新增可选字段 + 新 literal 值，安全。改字段名或语义，危险。

  3. 前后端契约必须同步改

    后端 Pydantic 改了，前端 types/*.ts 必须一起改。只改一边，运行时才报错，编译期发现不了。

  4. 改完必须三层验证

    后端 pytest → 前端 npm test → 真机点一遍。少一层就可能漏掉"测试过了但实际不能用"。

  5. 提交信息写清"为什么"

    "feat(router): 地图类问句路由到 3D" 比 "update router.py" 有用得多。 半年后你或别人看 git log 时，只有前者能帮你定位。
