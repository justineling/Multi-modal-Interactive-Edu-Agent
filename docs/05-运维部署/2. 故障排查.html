2故障排查

按症状分类的排查手册。每条都给「怎么确认是这个问题」的具体命令，不靠猜。

排查通用顺序：先确认后端活着（/api/health）→ 再用 curl 打一次目标接口 → 最后看前端控制台。先定位是后端问题还是前端问题，比直接翻代码快十倍。

启动类

后端起不来：ModuleNotFoundError

确认：

cd backend
.venv\Scripts\python.exe -c "import fastapi, sqlalchemy, pymupdf; print('OK')"

如果报错：依赖没装全。重新装：

.venv\Scripts\pip.exe install -r requirements.txt

如果是 sqlalchemy.ext.asyncio 报 ImportError： 缺 greenlet。SQLAlchemy 2.1 起它不再随主包安装，必须用 sqlalchemy[asyncio]。检查 requirements.txt。

后端起不来：Address already in use

# Windows：看谁占了 8000
netstat -ano | findstr :8000

# 杀掉（PID 换成上面查到的）
taskkill /PID 12345 /F

# 或者直接换端口
uvicorn app.main:app --reload --port 8001

前端起不来：EADDRINUSE

5173 被占。Vite 会自动找下一个端口（5174），看终端输出的实际地址。

前端 npm install 报 peer 冲突

不要用 --force 或 --legacy-peer-deps 糊过去。 冲突说明版本组合错了。检查这四个包的版本：

npm ls react react-konva @react-three/fiber tailwindcss
包必须错装的后果
@react-three/fiberv9v8 与 React 19 不兼容，3D 整块白屏
react-konvav192D 动画渲染失败
tailwindcssv3.4v4 是 CSS-first 配置，样式全不生效
katex0.16 线0.19 会与 rehype-katex 冲突，公式字体错位

上传与解析类

上传后一直 parsing，进度不动

确认后端是否还在跑：

curl http://127.0.0.1:8000/api/health

看后端日志有没有异常堆栈。如果后端进程挂了，解析任务会中断但状态停在 parsing。

手动查状态：

curl http://127.0.0.1:8000/api/documents/{doc_id}/status

返回 progress: 0 且长时间不变 → 任务没启动。检查 tasks.py 的日志。

上传报 PDF_NO_TEXT_LAYER

扫描版 PDF。验证方法：

cd backend
.venv\Scripts\python.exe -c "import pymupdf; d=pymupdf.open('path/to/file.pdf'); print(repr(d[0].get_text()[:100]))"

如果输出是 ''（空字符串），确认是扫描版，需要 OCR，当前不支持。

目录树只有「Page 1」「Page 2」

章节号识别失败。诊断：

.venv\Scripts\python.exe -c "import pymupdf; d=pymupdf.open('data/sample_textbook.pdf'); [print(p.number, repr(p.get_text()[:80])) for p in d[:5]]"

看真实文本里章节号长什么样，对照 pdf_parser.py 的正则。常见情况：

  • 章节标题是图片 → 正则可以匹配但文本里没有 → 无法识别
  • 用了罗马数字（Chapter IV）→ 正则需要扩展
  • 章节号在页眉/页脚，与标题分离 → 需要调整匹配策略

对话类

前端一直显示"生成中"，输入框不恢复

这是 SSE 没收到 turn_end。用 curl 直接看原始流：

curl -N -X POST http://127.0.0.1:8000/api/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"workspace_id":"xxx","query":"测试","mode":"syllabus_strict"}'
观察结果结论
有 event: turn_end后端正常，问题在前端解析器或事件分发
没有 turn_end，流直接断后端异常路径漏发兜底事件，看 chat_stream.py
完全没有输出请求被中间层缓冲，检查 nginx proxy_buffering off

什么问题都答"课本未覆盖"

三步诊断：

  1. 先确认教材解析成功：GET /api/documents/{id}/chunks?limit=5， 有内容说明切片正常。
  2. 看检索是否命中：在 SSE 的 retrieval 事件里看 top_score 和 grader_status。
  3. 算实词命中率： 
    .venv\Scripts\python.exe -c "from app.services.text_signals import content_words; print(content_words('你的问句'))"
    如果输出是空集合，说明全是虚词，永远命中不了。

如果阈值确实太高（新教材的实词分布不同），调低 GRADER_CONTENT_HIT_MIN_RATIO。 但必须同时验证无关问题仍被拒绝，否则会打开误判的口子。

无关问题也能得到回答

这是更危险的方向（会编造页码）。检查：

  • GRADER_CONTENT_HIT_MIN_RATIO 是不是被调太低了
  • retriever.py 里的 BM25 归一化是不是用了相对值 bm25 / max(bm25)（那是错的）
  • extract_section_code 是不是把裸数字当章节号了（"帮我写 3 首"里的 3）

画布渲染类

画布白屏

先看浏览器 Console 的红色报错。常见几种：

报错原因
Cannot read property 'map' of undefined某个数组字段是 null，渲染器直接 map 了
Cannot read property 'x' of undefinedposition 不是 3 元组，或字段名写错
LAYOUT_REGISTRY[layout] is not a function新布局没在注册表里登记
R3F: Hooks can only be used within Canvas3D 组件被渲染在 Canvas 外面

快速定位是哪一页出问题：在 SlideRenderer.tsx 的 map 里加 console.log("render slide", i, slide)，看最后一条日志的索引。

点画布元素没有锚点 chip

  1. React DevTools 里看 store 的 anchor 是否为 null
  2. 如果是 null → 点击事件没触发，检查元素上有没有 onClick
  3. 如果不是 null 但 chip 没显示 → AnchorChip 的渲染条件有问题

patch 后整个 PPT 都变了

这是最严重的一类 bug，通常是 update_node 被当成整体替换。

检查 useArtifactPatch.ts：

// ❌ 错
setAtPath(spec, op.node_path, op.payload)

// ✅ 对
const current = resolvePointer(spec, op.node_path);
setAtPath(spec, op.node_path, { ...current, ...op.payload })

3D 场景打不开

确认 WebGL 可用：浏览器打开 chrome://gpu，看 WebGL 是否 Hardware accelerated。

确认版本：npm ls @react-three/fiber 必须是 9.x。

确认 three 版本：必须是 0.186.x，与 fiber v9 配套。

性能类

长对话后界面卡顿

通常是 appendToken 每次创建新数组导致整树重渲染。检查 store 里是否只替换了目标消息对象：

// ❌ 每次 map 出新数组，所有消息组件重渲染
messages: state.messages.map(m => ...)

// ✅ 只替换目标，其余保持引用
messages: state.messages.map(m =>
  m.id === targetId ? { ...m, content: m.content + delta } : m
)

第二版虽然也 map 了，但未命中的对象引用不变，React 会跳过它们的重渲染。

2D 动画拖时间轴掉帧

检查 Konva 是否分层。一个 Layer 里放几百个元素必然卡。应该拆成背景 / 元素 / 交互三层。

数据类

重启后上传的 PDF 不见了

SQLite 相对路径锚定问题。确认两次启动的工作目录是否一致：

# 这样启动，db 在 backend/data/app.db
cd backend && uvicorn app.main:app

# 这样启动，db 在 ./data/app.db（项目根）—— 是另一个文件！
uvicorn app.main:app --app-dir backend

固定一种启动方式。推荐 cd backend 再启动。

检查有没有两个 db 文件：

dir /s /b app.db

刷新后对话没了

消息应该落库。检查：

curl http://127.0.0.1:8000/api/workspaces/{ws_id}/messages
  • 返回空数组 → 消息没落库，检查 agent_engine 的落库逻辑
  • 有数据但前端不显示 → useWorkspaceSession 的恢复逻辑有问题
  • 切到了别的工作区 → 看 localStorage 里的 currentWorkspaceId

版本历史里 v1 内容不对

检查是不是键序差异而不是内容差异。用 sort_keys 归一后再比对：

.venv\Scripts\python.exe -c "
import json, requests
a = requests.get('http://127.0.0.1:8000/api/artifacts/xxx?version=1').json()['data']['spec']
print(json.dumps(a, sort_keys=True, ensure_ascii=False)[:200])
"

如果排序后一致，说明只是序列化顺序不同，内容没坏。

还是查不出？

按这个顺序收集信息：

  1. 确认基线是绿的 
    cd backend && .venv\Scripts\python.exe -m pytest tests -q
cd ../frontend && npm test

    如果测试红了，先修测试——说明某个基础假设被破坏了，不是环境问题。

  2. 跑端到端冒烟 
    cd backend
.venv\Scripts\python.exe -m uvicorn app.main:app --port 8123
# 另一个终端
.venv\Scripts\python.exe ../scripts/e2e_smoke.py

    38 项里哪一项 FAIL，就定位到了具体环节。

  3. 抓 turn_id 的完整日志

    从 turn_start 事件拿到 turn_id，在后端日志里 grep 它，看这一轮走到哪一步断的。

  4. 最小复现

    用 curl 直接打接口，绕开前端。如果 curl 正常，问题一定在前端。
